# 应用规格与套餐关联方案

状态：设计建议，尚未修改线上应用的 CPU/内存限制。2026-11-04。

## 当前情况

应用容器统一使用 requests 100m CPU / 128Mi 内存，limits 1 CPU / 512Mi 内存，定义于 `control_plane/application_runtime.py`。套餐目前只控制模型额度、个人磁盘和应用数量，不包含可选应用规格。构建容器有独立的资源设置。

## 用户体验

用户发布项目时选择命名规格，展示 CPU 和内存；只能选择套餐允许的档位。超出套餐的档位展示升级入口，不允许仅靠前端校验。OpenHands 调用发布工具同样使用这些规则，不获得额外额度。

建议的单应用上限如下，具体套餐及价格由管理端配置：

| 档位 | CPU 上限 | 内存上限 | 建议允许的套餐 |
| --- | --- | --- | --- |
| 轻量 | 0.25 核（250m） | 256 MiB | 免费及以上 |
| 标准 | 0.5 核（500m） | 512 MiB | 基础付费及以上 |
| 增强 | 1 核（1000m） | 1 GiB | 高级付费 |

这些是资源上限，不承诺应用持续独占该 CPU。调度预留量由每档 requests 配置，必须小于等于 limits，页面明确区分。内存统一显示 MiB/GiB；不将用户口述的“250m 内存”直接写进 Kubernetes。

应用卡片提供“调整规格”：显示当前档位和可选档位，说明会触发重新调度，可能出现短暂中断。选择规格不重新构建镜像。调整成功、失败、回滚和待核验均有状态，实际生效前不把目标额度当成已生效额度。

## 三层额度

1. **单应用规格**：每个应用能选择的 CPU/内存档位。
2. **用户总额度**：同时处于运行、启动、发布或调整中的应用，合计预留的 CPU/内存不得超过套餐总额；应用个数另行限制。不能通过创建大量小应用绕过总量。
3. **节点可用量**：单节点先保留系统、共享服务、编程运行环境及 Kata 开销；允许购买的总容量须经过平台容量策略约束。不能仅以应用 limits 之和声称可以在节点上全部启动。

前两层在同一数据库事务内核验与预留，启动、发布、调整规格共用用户额度锁。停止或删除须观察实例确实退出后才释放运行预留。停止仍保留文件、镜像、数据库和应用名额。滚动更新暂时并存两个实例时也要计入额度，或者采用明确允许短暂停机的更新策略，避免额外实例在免费额度下长期卡住。

## 与费用的关系

- 注册赠送的 1 美元是模型调用额度，继续由 LiteLLM 计量；不把它混同为 CPU 额度。
- 套餐分别包含模型充值额度、运行规格与总量、磁盘和应用个数。付费不意味着无限期占用节点算力。
- 长期方案建议采用“按周期生效的算力权益 + 可单独充值的模型余额”。当前只做模拟支付，不能把现有一次充值流程宣称为已支持订阅、续费或到期回收。
- 套餐升级生效后可选择更高档位，不自动放大所有已有应用；降级不得静默削减正在运行的应用或删除数据。超额时阻止新增、展示处理方案；到期宽限与停机政策须单独明确后实施。

## 控制面与接口草案

以下为下一阶段契约设计，不是已经存在的接口：

- 套餐目录增加 `allowed_runtime_profiles`、`runtime_cpu_total_millicores`、`runtime_memory_total_mib`、同时运行数；规格目录明确 requests、limits 和版本。
- `GET /api/user/workspace/runtime-options` 返回该用户可选规格、当前资源预留和剩余总额度。
- 发布请求可带 `runtime_profile_id`。后端从套餐目录解析真实资源值，客户端不能自行提交任意 CPU/内存绕过目录。
- `POST /api/user/workspace/apps/{id}/resize` 提交档位与预期应用版本、幂等键。需用户拥有该应用、额度足够、无冲突运行任务。
- 应用分别保存期望规格、最后确认生效规格和资源变更任务。控制器核验 Deployment 与就绪情况后提交结果；写入结果不明进入既有待核验工作台；普通状态查询超时继续保留上次确认状态并重试。
- 审计记录谁在何时把哪个应用从哪档改到哪档，以及配额检查、执行、恢复结果。
- 现有应用保留当前资源参数作为历史规格，迁移不自动降配。新增应用再使用新默认档位；已有用户是否赠予过渡权益须由管理员明确配置。

## 构建与数据库

构建任务和 OpenHands 编程执行使用独立策略，不能套用免费应用的 256 MiB 上限。控制并发、超时和缓存计量，避免因应用规格太小导致所有构建失败。

使用数据库的应用卡片继续展示实际存储占用、预留容量和采样时间。共用 PostgreSQL 的每库实际占用继续计入用户逻辑存储总量；应用 CPU/内存档位不包含共享 PostgreSQL 服务本身的 CPU/内存。当前数据库预留容量不是 PostgreSQL 原生的严格单库硬限额，界面不得误标为可硬性阻断写入的上限。

## 实施与验收顺序

1. 套餐/规格目录、持久化迁移及用户总量预留；测试免费越级、并发启动、停止释放、额度不足和旧应用兼容。
2. 发布与调整规格接口、控制器，验证实际容器资源、失败回滚、超时自动重试、写入不明待核验。
3. 用户发布规格选择器、应用调整入口、管理员套餐配置；OpenHands 发布工具使用同一接口契约。
4. 模拟升级后规格解锁，实际发布与调整、观察 CPU/内存百分比分母同步变化；移除临时测试应用并核验预留释放。
