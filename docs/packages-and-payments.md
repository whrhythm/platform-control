# 套餐重设计与本地支付演练

更新：2026-11-06。项目入口已上线；本文件的新版套餐仅为本地可执行试点配置，尚未替换线上目录，模拟支付未在集群启用，不改变现有用户已生效的权益。

## 1 购买什么

面向“做出一个有用应用，并能持续修改和使用”的创建者。三个档位共享编程、文件编辑、发布追溯和导出能力；按模型预算、空间和运行额度区分，不把故障恢复或数据导出作为高价档专属。

建议正式经营采用月度资源订阅加模型预算。以下是待成本与付费意愿验证的试点报价，不是已验证的毛利或长期托管承诺。

| 权益 | 体验版 | 创作版 | 专业版 |
| --- | --- | --- | --- |
| 正式月费建议 | 免费 | ¥29 / 月 | ¥99 / 月 |
| 模型预算 | 注册赠送 US$1，仅一次 | 每期含 ¥10 等值美元预算 | 每期含 ¥40 等值美元预算 |
| 逻辑存储总量 | 2 GiB | 4 GiB | 8 GiB |
| 可保留应用数量 | 1 | 5 | 10 |
| 单应用 CPU / 内存上限 | 0.25 核 / 256 MiB | 0.5 核 / 512 MiB | 1 核 / 1024 MiB |
| 全部运行应用 CPU / 内存总上限 | 0.25 核 / 256 MiB | 1 核 / 1024 MiB | 2 核 / 2048 MiB |
| 数据库总上限 / 单库上限 / 数量 | 128 MiB / 128 MiB / 1 | 512 MiB / 256 MiB / 2 | 2048 MiB / 512 MiB / 4 |
| 普通“运行代码”每自然月次数 | 30 | 300 | 1000 |
| 普通“运行代码”单次时限 / 并发 | 10 秒 / 1 | 15 秒 / 1 | 15 秒 / 2 |

应用数量是保留名额，所有运行应用仍受总算力约束，不表示每个名额都能同时用满单应用上限。数据库、镜像、文件、依赖及应用持久数据计入逻辑总空间，数据库配额不是额外赠送空间。普通“运行代码”与 OpenHands 编程任务不同；后者继续按现有 Agent、构建配额和模型预算限制。

可校验配置见 [`config/plans-local-pilot.json`](../config/plans-local-pilot.json)。配置仅使用已有 CapacityPlan 字段，未增加所有工作器必须同步理解的新策略字段。体验赠送美元额度仍由既有一次性发放逻辑负责。

**本批只能模拟单次购买**。代码尚没有月度订阅账期、到期和续费状态，因此 JSON 名称标注“模拟”，描述为“本地单次测试购买”。不能把模拟完成展示成正式月费已开通，更不能宣传一次付款获得永久托管。正式月费上线须完成第 5 节。

## 2 金额、额度与权益分别计算

订单售价、模型额度、结算汇率和资源快照分别保存：

- 售价是本次实际应支付的人民币。例如创作版订单 ¥29。
- 其中 ¥10 为模型预算，不是把售价 ¥29 全部充入 LiteLLM。
- 汇率为 **1 美元对应多少人民币**。配置为 7 时，¥10 / 7 = US$1.428571，按现有微美元精度向下截取。旧订单保持创建时的汇率。
- 不承诺固定 tokens 数。模型、输入输出比例不同，tokens 可用量不同；用户看到实际美元余额、实际消耗和明确标注参考模型的估算。
- 同档重复购买可增加模型预算，但资源容量和应用名额不重复累加，不降低既有较高权益，不清零当月代码运行次数。
- 管理员改目录只影响后续报价和新订单；已创建订单按原价与原权益处理。旧用户不批量改配额，之后迁移也须单独确认规则。

下一步应将“模型充值包”独立成商品类型，让用户只补充模型预算；本批未用假资源升级冒充纯充值。

## 3 本地支付闭环

已实现真实回环 HTTP 的流程：创建平台订单 → 签名请求模拟器 → 本地收银台 → 模拟付款 → 模拟器发送签名通知 → 平台校验 → 既有模型充值控制器 → 既有资源开通控制器 → 用户权益更新。

平台从服务端订单快照取金额，不相信浏览器传来的价格或用户 ID。打开收银台、访问返回页面都不确认付款。只有验签、商户、订单、金额及状态都通过的通知才能确认；订单确认与资源开通分开。

本批接口：

- `POST /internal/v1/workspace/capacity/orders/{id}/checkout`：保存付款意图，再发下单请求；同一订单不会重复创建付款意图。
- `GET /internal/v1/workspace/capacity/orders/{id}/payment`：仅所有者可查询。
- `POST /payments/xunhupay/notify`：表单通知验签；成功应答精确为 `success`。
- LibreChat 提供对应身份代理与套餐页收银台入口；只有 `payment_provider=xunhupay_local` 时显示，默认仍为原有测试方式。前端返回后只查询，不自动授予权益。

状态规则：

| 情况 | 处理 |
| --- | --- |
| 重复付款通知或并发通知 | 同一交易只确认一次，不重复增加充值或资源开通次数 |
| 同一交易号用于另一订单 | 拒绝，数据库唯一约束兜底 |
| 回调签名或金额不一致 | 拒绝，不发权益 |
| 下单返回超时或无法验签 | 标记待核验，不盲目重下单；后续有效通知可恢复确认 |
| 下单进程中断，未保存返回结果 | 查询时超过 60 秒转为待核验，不一直显示正在创建；有效通知仍可恢复 |
| 已取消订单收到成功通知 | 记录已付款、待核验，不自动开资源；重复通知不重复审计 |
| 付款成功、模型充值或资源开通未完成 | 保留已付款事实及原权益，显示开通中或失败；按既有控制器恢复，不再次收费 |
| 仅网页跳转或收银台已打开 | 不确认付款 |

`payment_receipts` 通过迁移 `0021_payment_receipts` 保存付款意图及唯一交易号；非空表拒绝直接降级删除。2026-11-06 随售后工单样板迁移 `0022_business_templates` 一并在集群应用，API 与迁移镜像同步更新，并给 API 角色该表 SELECT/INSERT/UPDATE 权限。支付代码和表存在不代表支付已经开放：线上模拟支付开关仍关闭，新套餐目录未激活。

## 4 模拟器使用与协议边界

协议依据：[虎皮椒支付下单文档](https://www.xunhupay.com/doc/api/pay.html)。V3 产品的下单参数 `version` 为 `1.1`。按文档对非空标量参数排除 `hash`、按 ASCII 键排序、原值拼接 `key=value&...`，末尾直接追加密钥后计算 UTF-8 MD5；不对值做 URL 编码后再签名。

模拟器文件：`scripts/xunhupay_simulator.py`。它仅监听 `127.0.0.1`，只接受以 `sim-` 开头的测试 AppID、至少 32 字符的测试密钥和回环通知地址；适配器不允许把本次测试配置指向真实支付网关。

在 WSL 的 platform-control 目录执行：

```bash
# 仅在当前终端生成测试密钥，不写入 Git，不打印密钥。
export XUNHUPAY_SIM_SECRET="$(python3 -c 'import secrets; print(secrets.token_hex(32))')"
export XUNHUPAY_SIM_APPID=sim-starbridge
.venv/bin/python scripts/xunhupay_simulator.py --port 9066 \
  --notify-url http://127.0.0.1:8088/payments/xunhupay/notify
```

本地商户 API 使用独立测试数据库及测试登录配置；与模拟器使用同一个测试密钥，并设置：

```text
PLATFORM_TEST_PAYMENTS_ENABLED=true
PLATFORM_CAPACITY_UPGRADES_ENABLED=true
PLATFORM_XUNHUPAY_SIMULATOR_ENABLED=true
PLATFORM_XUNHUPAY_SIMULATOR_URL=http://127.0.0.1:9066
PLATFORM_XUNHUPAY_NOTIFY_URL=http://127.0.0.1:8088/payments/xunhupay/notify
PLATFORM_XUNHUPAY_APPID=sim-starbridge
PLATFORM_XUNHUPAY_SECRET=<与模拟器相同的临时测试密钥>
```

已有平台的身份校验保持开启；不是启动模拟器就能绕过登录创建订单。LibreChat 的服务代理继续要求 HTTPS；如手动将本地 LibreChat 连到本地商户，需使用可信本地 HTTPS 反向代理，不能放宽服务代理规则。云端页面里的 localhost 指向访问者电脑，因此本地配置不得直接启用在集群。

无需手工建测试用户、数据库或凭据的自动演练：

```bash
.venv/bin/python -m pytest tests/test_payments.py -q
PLATFORM_TEST_POSTGRES_IMAGE=postgres:16 .venv/bin/python scripts/test_postgres.py
```

演练自动创建临时 SQLite / PostgreSQL、模拟身份和两个回环 HTTP 服务，结束即关闭。模型预算和资源扩容的外部系统使用测试替身；真实的控制器状态转换与读后核验仍执行，不访问真实 LiteLLM 或集群，不冒充真实扩容。

模拟器订单保存在内存，重启后清空；本地平台已记录的付款意图不会因此自动重复下单。模拟器支持按钮重发通知，尚不模拟提供方的定时重试、查询、退款、对账和二维码支付。参考[官方查询文档](https://www.xunhupay.com/doc/api/search.html)仍需单独实现并核实，不从支付接口推断未确认的协议。

## 5 正式收费前的下一阶段

1. 支付提供方查单与定时对账：处理服务重启后未决下单、丢失回调，落到管理员付款待核验队列。当前只有持久记录和审计，没有支付人工处理页面。
2. 账期与续费：每次续费生成新订单；未付款不增加额度，付款不重置历史消耗。开通延迟的账期起点应按服务实际可用时间确认。
3. 到期与保留：提前通知，先限制新增消耗和新发布；按明示的宽限期决定是否暂停运行。文件和数据库不因欠费自动删除，保留期、导出和最终销毁必须分别告知。
4. 退款与补偿：明确尚未消耗模型额度、已消耗模型费用和资源服务费的规则；部分开通不能仅回退数据库状态。增加退款账本和审计。
5. 确认正式价格与供应成本，完成提供方真实测试订单验证，再启用真实收款。
