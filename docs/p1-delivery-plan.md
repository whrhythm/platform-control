依据：[产品纲领](product-charter.md)、[P0 现状核查](p0-audit-20261106.md)。截至 2026-11-07：P1-00 契约验证、P1-01 私人项目创建与助手绑定已交付；P1-02 知识导入/检索/原文引用/清理的核心流程已部署并通过指定账号 UI 和最终镜像回访，见[知识交付记录](p1-knowledge.md)。P1-03 固定草稿试用、迭代和真实回答验收已部署并完成三轮指定账号验证及最终镜像回访，见[试用交付记录](p1-trials.md)。性能门禁未通过，最终回访有一次上游中断后人工重试成功，不宣称稳定或商业可用。P1-04 正式发布、受邀成员访问和创建者实际扣费已部署，三轮发布/成员使用及权限、预算 UI 验证见[发布交付记录](p1-releases.md)。最终回访出现一次模型连接中断，明确重试后成功。下一步为 P1-05，整个 P1 的多日稳定性门槛尚未满足。

## 1 交付结果与设计取舍

P1 要交付的是：创建者在现有聊天产品中创建一个知识助手，导入合成售后资料，在测试对话中验证回答，修改指令或知识后重新验证，再发布给指定登录用户；线上版本不受草稿修改影响，费用归属清楚，回到项目能继续维护。

P2 在同一项目上增加创建和查询工单，让助手从回答问题扩展到完成业务任务。已有工单页面和数据库复用，不新增一个独立的“AI 应用平台”入口。

- **执行基础：** 优先复用 LibreChat 的 Agent、Skill、文件检索、会话与 ACL；OpenHands 保留为开发助手。P1-00 验证兼容性后再选择具体适配方式，不预先承诺原生执行器已经满足固定版本运行。
- **项目主记录：** 控制面项目承接产品归属、权益与发布状态；显式绑定 LibreChat Agent、可选聊天项目、知识集合。两个数据库不做隐式跨库事务；通过版本、幂等请求和可重试状态协调。
- **发布：** 服务端解析 release ID，读取不可变配置/知识版本与当前授权。浏览器不能提交任意 Agent 配置覆盖发布版本。发布快照保存凭据引用，权限撤销须立即约束后续调用，不能因“版本固定”继续使用已撤销权限。
- **身份与费用：** 分开创建者、使用者和付费账户。模型请求保留实际调用者与 sponsor 身份，服务端验证访问和预算，不把创建者密钥交给使用者。
- **知识更新：** 新资料先形成草稿索引；正式版本保留其所需索引，删除与回收检查引用和保留规则。撤销访问立即生效，不能以旧版索引仍存在为由泄露已撤销资料。
- **访问方式：** 首批复用现有内部域名，只向受邀已登录用户开放应用入口。公网匿名访问、自定义域名和工作流引擎暂缓。

## 3 最小状态与版本约定

- 项目绑定：未绑定 → 准备中 → 可编辑；失败保持项目可见并提供幂等重试，不能当成项目不存在。
- 知识导入：已上传 → 索引中 → 就绪 / 失败；新版本就绪并确认发布前，线上保持旧版本。
- 试用：加载中 → 可对话 / 执行中 / 待确认 / 失败 / 已停止；显示本次草稿版本，不以“有聊天回复”替代工具成功。
- 发布：已受理 → 校验中 → 生效 / 失败 / 结果待核验；线上当前版本与最近尝试分开显示。
- 调用记录关联：actor、owner/sponsor、project、release 或 draft revision、session、request ID、用途、预算与结果；可见日志不保存明文密钥或私密推理。
- 快照包含：Agent 指令与参数、允许模型、Skill 内容/版本、知识文件和索引版本、工具定义与授权引用、必要代码/镜像。任何影响行为的改变都使旧试用确认失效。
- 跨服务写入先记录意图，失败可恢复；不要求为了看起来成功而手工改 MongoDB/PostgreSQL。撤销权限与可用余额每次调用重新准入，不完全依赖缓存快照。

## 5 重复验收方法

先固定模型与路由版本、部署镜像、测试资料摘要、负载和数据量。初始性能样本为 1 个并发任务、已就绪应用、同一小型知识集；冷启动另记，不能混进平均值或只挑最快的一轮。

每轮完整路径：创建/打开项目 → 导入资料并索引 → 测试有依据与无依据问题 → 修改知识/行为 → 再试用 → 确认发布 → 受邀身份访问 → 返回修改并再次发布。连续 3 轮通过后，按纲领累计不少于 20 次完整尝试及多身份/多日测试。记录所有失败与人工帮助，不能只登记成功次数。

任务期限初始配置候选：测试对话总时限 120 秒、单次知识导入 180 秒、单个受控工具调用 60 秒；达到时限必须给出终结或核验状态。它们是故障处理期限，不是可接受响应速度；首次有效回答仍以纲领的 p95 10 秒目标验收。P1-00/02 在隔离环境测量后固定配置与成本上限，调整须先记录依据。

界面检查至少覆盖亮/暗主题、窄屏、键盘、空状态、加载失败、停止和刷新；正式会话与开发/试用会话不得混用。后台脚本可测机制，UI 完整流程必须走产品入口；本轮 P0 只读脚本不计作一次交付验收。

```text
用例 / 轮次：
代码提交 / 镜像 / 配置版本 / 模型路由：
测试资料摘要 / 身份类型 / 数据范围 / 并发条件：
用户操作与预期：
实际结果及可核验业务记录：
受理 / 首段有效回答 / 就绪 / 发布完成耗时：
模型与资源消耗 / 计费归属：
失败、重试、人工介入：
证据位置 / 是否通过 / 遗留问题：
```

## 6 迭代与商业门槛

P1/P2 内测不顺带改套餐价格、启用真实支付或批量迁移旧用户。新业务调用的预算准入是 P1 必需能力；月费、续费、退款和商业定价留在 P4，用实际任务成本验证。

进入真实客户数据试点前必须补独立备份及恢复证据；进入真实收费前必须验证实际支付与履约。这些条件未满足时，只进行明确标注的合成数据内测。未通过核心流程时不接入新工作流引擎或市场功能。
