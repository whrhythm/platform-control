## 1 交付结果与设计取舍

P1 要交付的是：创建者通过现有聊天产品准备一个助手，按需选择知识、方法和工具，试用后发布给指定登录用户；线上版本不受草稿修改影响，费用归属清楚，回到项目能继续维护。主验收使用合成知识助手，同时验证不需要知识的助手不会被迫上传资料、编程或部署。

P2 在同一项目上增加受控业务读写，以创建和查询工单验证权限、确认、幂等与数据保留。复用已有配套页面和数据库；不向每个项目默认安装工单模块，也不新增独立的“AI 应用平台”入口。

- **执行基础：** 优先复用 LibreChat 的 Agent、Skill、文件检索、会话与 ACL；OpenHands 保留为开发助手。P1-00 验证兼容性后再选择具体适配方式，不预先承诺原生执行器已经满足固定版本运行。
- **项目主记录：** 控制面项目承接产品归属、权益与发布状态；显式绑定 LibreChat Agent、可选聊天项目、知识集合。两个数据库不做隐式跨库事务；通过版本、幂等请求和可重试状态协调。
- **发布：** 服务端解析 release ID，读取不可变配置/知识版本与当前授权。浏览器不能提交任意 Agent 配置覆盖发布版本。发布快照保存凭据引用，权限撤销须立即约束后续调用，不能因“版本固定”继续使用已撤销权限。
- **身份与费用：** 分开创建者、使用者和付费账户。模型请求保留实际调用者与 sponsor 身份，服务端验证访问和预算，不把创建者密钥交给使用者。
- **知识更新：** 新资料先形成草稿索引；正式版本保留其所需索引，删除与回收检查引用和保留规则。撤销访问立即生效，不能以旧版索引仍存在为由泄露已撤销资料。
- **访问方式：** 首批复用现有内部域名，只向受邀已登录用户开放应用入口。公网匿名访问、自定义域名和工作流引擎暂缓。

## 3 最小状态与版本约定

- 项目绑定：未绑定 → 准备中 → 可编辑；失败保持项目可见并提供幂等重试，不能当成项目不存在。
- 知识导入：已上传 → 索引中 → 就绪 / 失败；新版本就绪并确认发布前，线上保持旧版本。
- 试用：加载中 → 可对话 / 执行中 / 待确认 / 失败 / 已停止；显示本次草稿版本，不以“有聊天回复”替代工具成功。
- 发布：已受理 → 校验中 → 生效 / 失败 / 结果待核验；线上当前版本与最近尝试分开显示。
- 调用记录关联：actor、owner/sponsor、project、release 或 draft revision、session、request ID、用途、预算与结果；可见日志不保存明文密钥或私密推理。
- 快照包含：Agent 指令与参数、允许模型、Skill 内容/版本、知识文件和索引版本、工具定义与授权引用、必要代码/镜像。任何影响行为的改变都使旧试用确认失效。
- 跨服务写入先记录意图，失败可恢复；不要求为了看起来成功而手工改 MongoDB/PostgreSQL。撤销权限与可用余额每次调用重新准入，不完全依赖缓存快照。

| F01 文件来源 | 从附件与持久文件入口查看同一资料、预览和编辑 | 来源/所属项目/是否为副本清楚，保存结果与引用状态正确 |
| F02 资产计量 | 引用同一资产、另存副本、建立索引并删除未引用副本 | 按公布口径计量；同对象多入口不重复收取，实际副本和派生索引不能漏计 |
| F03 删除与引用 | 删除聊天、附件、项目文件与被发布版本引用的知识 | 分别展示影响，授权和引用检查通过；不因删聊天丢持久项目，不误删线上依赖 |
| M01 维护与退出 | 停用/恢复、查看旧新版本、导出承诺范围资产 | 数据保留、恢复重新准入；导出清单可读且不含密钥/他人资料，未支持的依赖明确说明 |
| T01 建单 | 用户确认创建一条演示工单，重复提交同一操作 | 实际仅一条记录，返回可查询编号；模型自称建单不能算通过 |
| T02 查单权限 | 查询本人、授权团队及未授权工单 | 仅返回明确授权范围，拒绝跨应用及越权查询 |
| T03 修改与发布 | 修改配套页面后重新发布，再读取原记录 | 工单及账号保留；新版本生效；失败版本不破坏旧业务服务 |
| T04 未知写入 | 建单成功但响应丢失 | 核验同一业务请求结果，不盲目创建第二条记录 |

K/A/U/F/M 为 P1 门槛，T 为 P2 门槛。当前已获准使用指定创建者及两个专用合成成员账号；授权不扩展至其他真实用户。三个账号只能证明多身份，不能替代三位真实目标用户的无协助测试；后者需要产品负责人组织。知识与业务用例按实际版本断言，不将某一份演示资料固定为所有应用规则。

## 5 重复验收方法

先固定模型与路由版本、部署镜像、测试资料摘要、负载和数据量。初始性能样本为 1 个并发任务、已就绪应用、同一小型知识集；冷启动另记，不能混进平均值或只挑最快的一轮。

每轮完整路径：创建/打开项目 → 导入资料并索引 → 测试有依据与无依据问题 → 修改知识/行为 → 再试用 → 确认发布 → 受邀身份访问 → 返回修改并再次发布。连续 3 轮通过后，按纲领累计不少于 20 次完整尝试及多身份/多日测试。记录所有失败与人工帮助，不能只登记成功次数。

正式调用已有默认 120 秒、最多 4 步等边界，见发布记录。知识索引和后续工具的实际期限在对应版本测试前核对，不能把早期候选 180/60 秒当作已实现证据。达到期限必须终结或进入明确核验状态；期限不是可接受响应速度，不因超时自动重放。

质量目标沿用纲领：1 秒内受理或说明连接状态；已就绪普通测试对话首次有意义回答 p95 ≤ 10 秒；等待超过 10 秒解释所处阶段；每条已承诺场景连续 3 轮成功后，累计至少 20 次完整尝试且至少 19 次成功，覆盖 3 个独立身份、2 个测试日；至少 3 位目标用户无协助完成首次使用与返回修改。所有越权、重复收费/写入、误删和版本错发用例必须通过，不能用平均值抵消失败。完整回复耗时不能冒充首段延迟，三轮局部发布不能冒充整条任务通过。

界面检查至少覆盖亮/暗主题、窄屏、键盘、空状态、加载失败、停止和刷新；正式会话与开发/试用会话不得混用。后台脚本可测机制，UI 完整流程必须走产品入口。性能门禁、跳过测试、人工修复和失败都如实记录；脚本登录调整和后台数据修补也要区分。

```text
用例 / 轮次：
代码提交 / 镜像 / 配置版本 / 模型路由：
测试资料摘要 / 身份类型 / 数据范围 / 并发条件：
用户操作与预期：
实际结果及可核验业务记录：
受理 / 首段有效回答 / 就绪 / 发布完成耗时：
模型与资源消耗 / 计费归属：
失败、重试、人工介入：
证据位置 / 是否通过 / 遗留问题：
```

## 6 迭代与商业门槛

P1/P2 内测不顺带改套餐价格、启用真实支付或批量迁移旧用户。新业务调用的预算准入是 P1 必需能力；月费、续费、退款和商业定价留在 P4，用实际任务成本验证。

进入真实客户数据试点前必须补独立备份及恢复证据；进入真实收费前必须验证实际支付与履约。这些条件未满足时，只进行明确标注的合成数据内测。未通过核心流程时不接入新工作流引擎或市场功能。

### 数据与商业开放的依赖

- **当前外部条件：**用户之前确认暂没有独立备份存储；仍按此作为未解决依赖，不能因为本地恢复成功而写成灾备就绪。到 P3-02 前由产品负责人提供或批准目标，工程方设计并执行恢复验证。
- **访问条件：**当前证据来自内部域名和局域网。对外范围、域名/DNS、可信 TLS、身份验证与注册策略须在外部试点前确定；不能把用户手工配置 hosts 或浏览器证书例外作为客户正常使用流程。
- **目标用户：**现有三个验收账号不是三位独立目标用户。由产品负责人组织无协助测试与访谈，工程方提供固定任务和记录；不得编造访谈、消费或续费结果。
- **支付与支持：**商户环境、经营条款与隐私告知、收费授权、售后联系人及支持时段由负责人落实；技术只在明确授权范围内验证。不因阶段计划存在就创建真实订单或对外发送邀请。
- 依赖缺失只阻止依赖它的门槛，不阻止内部合成数据下的权限、体验、故障及恢复机制改进。不得用等待域名或存储为理由停掉所有可完成任务，也不得绕过依赖宣布商用。

## 8 稳定性、安全与扩展能力的专项门禁

### 跨阶段安全检查

| 风险边界 | 必须检查的行为 | 未通过的处理 |
| --- | --- | --- |
| 身份和原生旁路 | 同一主体在不同资源的权限；会话过期/撤销/禁用账号；平台入口与原生 Agent、文件、来源、导出及直接接口一致 | 阻止相应分享与外部试点，优先修；不能仅隐藏按钮 |
| 租户与资产 | 替换项目/用户/版本/文件 ID，跨项目检索、下载和引用；共享 DB/对象存储权限；资产路径与压缩包路径越界 | 越权和数据误删零容忍；保存拒绝证据，不依赖模型自觉 |
| 指令和工具 | 恶意文档/Skill/工具结果、未经批准网络目标、凭据窃取指令；写操作参数在确认后变更 | 不得扩大权限；生成文本不等于真实执行；对未支持能力明确拒绝 |
| 执行环境 | OpenHands/运行代码/构建任务实际隔离方式、权限、出口、卷与 Secret；禁用或失败时不能悄悄降低隔离 | 若隔离目标未实测，不扩大不可信代码用户范围；安装 Kata 本身不是证明 |
| 预算与资源 | 并发请求、耗尽、取消、超时、重启和过期统计；模型、运行代码、构建、文件/索引/DB 等实际支持项 | 不无限执行、不重复扣费；计量未知显示待核验；未具备的硬限制不得宣传为已强制 |
| 凭据与审计 | 浏览器、快照、导出、错误与日志中的密钥；权限变更和管理员核验可追溯；管理员最小权限 | 不输出凭据或私人内容；发现暴露按事件处理并安排受控轮换，不把审计日志当任意读用户数据的授权 |
| 供应链与升级 | 锁定依赖/镜像、已知风险检查、更新测试及回退；DB/worker/API 的混合版本兼容 | 未评估的高风险更新不进发布；修复已知问题不能以测试多为理由拖延 |

关键权限、跨租户、凭据、数据误删、不可控消费与重复写入问题不允许带着进入下一开放阶段。其他未修缺陷须明确影响范围、临时处理、责任人和复查点；没有可用绕行的核心任务阻塞同样阻止发布。发布前完成一次不只重复实现者自测路径的复核，记录覆盖范围及未覆盖项，不将工具扫描通过称为完整安全证明。

### 稳定性与容量的执行方法

1. 固定候选镜像、模型路由、数据规模、预算上限、负载脚本与测试窗口。以 1 并发测基线，再在隔离/受控环境逐级增加到候选支持值；候选值在测试前登记，不能用达到资源极限的尝试替代产品支持容量。
2. 除成功路径外，注入模型超时/限流、知识服务不可达、数据库短暂断开、worker 重启、回执丢失、磁盘不足、取消与重复提交；检查实际停止、状态恢复、费用与清理。优先在隔离环境执行破坏性故障，不为了验收中断现有用户。
3. 候选发布先做至少 1 小时稳态负载测试，再做至少 24 小时受控观察，包含高峰与空闲、限额和恢复；测延迟分布、错误率、队列积压、内存/磁盘增长、孤儿任务和费用差异。此为待执行的内部门槛，不是已测成绩或生产 SLA。
4. 报告区分受理、首次有效输出、最终完成、冷启动和外部供应商等待；记录所有失败。达到支持上限时有明确排队/拒绝和预算行为，不出现无限等待；关键指标未达到则缩小候选支持范围或修复后复测，不能隐藏失败后放行。
5. 发布通过 GitOps 固定版本，迁移前备份，检查所有持久策略消费者兼容；验证回退不会撤销必要权限校验或损坏用户数据。数据库迁移不盲目降级，代码回退与业务数据恢复分开处置。

### 扩展能力的排期边界

| 能力 | 纳入条件 | 交付边界 |
| --- | --- | --- |
| 外部 Skill | 主任务确需方法复用，且 P1 权限/资产边界已通过 | 先纯指令/受控资源，再按需求支持脚本；固定来源/许可/版本、权限与依赖检查，试用后绑定发布；原生可导入不等于正式助手可安全使用 |
| 嵌入组件/模型升级 | 安全维护、兼容性或明确检索质量需求 | 保留来源与旧索引，新模型重新索引并验证/切换/回退；升级自身需要修复时优先处理，不为追版本打断主任务 |
| OpenHands 自定义开发 | 现有工具不能完成已选业务任务 | 只创建必要接口/页面，沿用项目、预算、审批、持久数据和部署控制；不变成所有助手的必经步骤 |

## 9 交付记录、职责与变更控制

### 每一任务的完成定义

每张实施任务记录必须包含：编号与依赖、目标用户任务、UI 入口及非目标、涉及数据/权限/费用、旧数据迁移与回退、正常/失败/刷新/取消状态、确定性检查与真实 UI 用例、部署版本与证据、遗留问题及下一步。遵循纲领第 10 节格式；没有证据不能把状态从“已实现”跳到“已验收”。

开发负责人负责方案、实现、迁移、测试与技术文档；产品负责人确认支持范围、目标用户任务、费用与商业条款；运维/安全复核责任人负责恢复、风险与发布证据复核。小团队可以兼任，但必须在任务中写明责任人，不能把“AI 测试通过”作为无人负责的签字。没有复核人员时标记门槛缺失，不能假称独立评审完成。

每个阶段评审给出：通过、带明确非关键遗留项通过、未通过三种结论。关键权限/数据/费用或核心任务失败不得带条件通过。依赖未满足时完成不受影响部分，并准确列出阻塞项；不以时间或 token 用尽为依据结项。

### 排期与范围

本计划给出依赖顺序，不在缺少容量、试用用户和外部条件时承诺商用日期。恢复开发后按每一纵向任务拆小批次，先复现断点、实现最小完整修复、再发布验收；用前两批实际工作量和缺陷密度更新后续时间估算。估算必须注明假设和外部依赖，不能承诺固定日期换取降低门槛。

新增能力必须回答：服务哪类目标用户、解决哪段任务、为何已有能力不够、权限/成本/维护影响、如何验证、当前批次要移出什么。未解决核心断点时，默认暂缓新模型选择器、新引擎或市场扩展。
