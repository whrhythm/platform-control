# 统一套餐与配额管理

## 实施阶段

1. 目录与已生效权益分离：售价、模型额度、存储、发布应用、数据库、OpenHands、镜像构建、聊天代码运行统一配置。
2. 后端准入与执行：按用户锁串行检查申请；任务携带权益快照；实际执行资源和时限来自快照。
3. 两端显示与验收：管理员保存目录，用户看到已生效权益、目录报价、开通进度和已分配用量。
4. 后续独立阶段：管理员针对已有用户的权益调整单（预检、审批、审计、开通观测）、跨服务统一硬写入限制、订阅有效期与续费。当前不提供自动降级、真实收费或到期删除数据。

## 管理员操作

进入 Platform Control → 平台管理 → 套餐与配额管理。

- 售价和包含的模型额度相互独立。例如售价 10 元、模型额度 5 元，结算汇率为 7 时，订单应增加 0.714285 美元模型预算，而不是 1.428571 美元。整数微美元向下取整，LiteLLM 用户与虚拟 key 同步增加，已消费金额保留。
- 逻辑总容量包含文件、缓存、数据库、对象和镜像的实测用量；数据库等分项上限不增加总量。它与底层 PVC 的实际大小不是同一个指标。
- 发布应用配置单应用 CPU/内存、最多应用数，以及所有应用合计 CPU/内存。合计按分配的 limits 预留，不是瞬时 CPU/内存使用率。
- 数据库配置总预算、单库预留/警戒额度和数量。创建时检查预算；已有数据库沿用原预留，实际占用仍计量。数据库目前不提供硬字节写入限制。数据库预算不得大于总存储，单库预留不得大于数据库总预算。
- OpenHands 配置命令 CPU/内存、命令最长时间、任务最长时间和同时任务数。任务时限包含审批等待。同一工程及其上下级目录只允许一个活跃任务；不同工程可按额度并发。
- 镜像构建配置 CPU/内存、最长时间与并发。内存必须包含构建临时缓存与执行开销；构建 Pod 使用 Kata。发布失败清理和不明确写入核验沿用既有流程。
- 聊天运行代码配置每月次数、最长时间和并发。当前引擎支持最长 15 秒、最多并发 2，程序内存固定 256 MiB；界面不提供尚未支持的内存档位。次数按北京时间自然月重置，升级不重置已用次数。

保存成功意味着目录版本更新，不意味着给所有现有用户批量充值或扩容。普通聊天/OpenHands 默认模型及允许模型仍是平台级设置。注册一次赠送 1 美元的规则保持不变。

## 用户生效流程

在 LibreChat 个人菜单 → 套餐与用量查看当前已生效权益。套餐卡片的“查看完整资源配额”展示该次报价；它不能替代当前权益。应用合计“已分配”与应用监控中的瞬时占用率分开标注。

选择套餐 → 创建冻结报价的订单 → 确认模拟支付 → LiteLLM 两级额度到账 → 原个人卷完成扩容与观测 → 激活权益。后台配置在订单创建后发生改变，不改写这笔订单。重复确认不重复发放额度；资源开通失败保留已有权益及文件，可按原订单重试。

重复购买较低档位可以充值，但保留已开通的更高资源权益。新增资源权益统一采用逐项不降低规则，资源额度不会按订单次数累加。已运行应用和已提交任务继续使用原执行快照；新发布/启动及新任务使用当前已生效权益。

停止或删除应用完成观测前不释放合计额度；失败任务仍保留旧服务时继续占用额度。新发布使用 Recreate 更新，避免滚动更新额外启动一份服务突破已分配额度，因此替换期间可能短暂不可用。

## 接口与兼容性

现有管理员 `/v1/admin/ai` 和用户 `/internal/v1/workspace/capacity` 保持不变。新增权益字段保存在已有 JSON 快照；无需数据库表迁移。`quota_usage` 返回应用已分配 CPU/内存、数据库数与预留、活跃编程/构建数和权益更新时间；不把这些数字称为实际算力消费。

旧快照缺少字段时使用兼容默认值，严格拒绝未知策略字段。发布必须先升级所有策略读取者，尤其 agent-worker、workspace-controller、application-controller、model-billing-controller 和 MCP gateway，再开放新管理页保存。不能仅部署 API 后就把新字段写入共享策略。

共享节点资源不足仍可能导致等待调度。套餐 CPU/内存上限不是独占算力承诺；平台全局运行保护与用户额度同时有效。数据库警戒、服务原生限额与逻辑总量计量不等于已经实现跨服务统一硬限额。

验收使用一次性本地数据验证改价、半额模型充值、冻结报价、先到账后开通、幂等、超额拒绝与旧权益保留；真实用户仅核验界面和已生效权益，管理员仅核验读取/保存，不通过直接 SQL 修改业务账号额度。
