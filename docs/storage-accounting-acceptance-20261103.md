## 真实界面结果

1. 多次重新登录，Storage & plan 均显示同一个已就绪私有对象存储。数据库中该个人环境只有一条对象分配记录；原个人 PVC UID 保持 19e17f16-8d3b-43ff-9480-9baa3d0c8faa，容量仍为 4 GiB。
2. 五类来源均有新鲜样本，界面显示 Measured logical storage。文件额度 4 GiB，数据库和对象各 256 MiB，原 Harbor 项目实际无限额度如实显示，没有自动缩小既有权益。额外应用 PVC 经完整归属核验为零。
3. 在 Coding 聊天创建 codechat-objects-20261103，文件树可预览生成的 app.py；通过文件上传入口交付 test_objects.py 和 test_http.py，依赖安装在该工程自己的 .venv，缓存使用个人卷。
4. Coding 执行对象连接测试并提交构建、推送与部署。第一次构建成功，但服务返回 HTTP 500；界面出现发布失败通知和说明，失败实例停止并回收，文件、对象及两个原应用保留。
5. 一轮自动排查达到 180 秒上限，明确结束，没有声称发布成功。随后通过同一聊天修正 MinIO 上传需要二进制流的代码问题，并使用上传的真实 HTTP 测试后显式重新提交同一应用。最终成功版本实际可访问；没有创建第二条同工程应用记录。
6. 最终浏览器连续访问返回 CodeChat objects: 36、37；从应用卡片 Stop 到 Stopped，再 Start，返回 41，存储计数保持。健康检查也会访问根路径，因此不要求计数恰好加一。
7. 两个原应用通过 UI 打开仍分别返回 Hello CodeChat v3 和 PostgreSQL 递增计数。原 app.py 的 SHA-256 仍为 1bb3352a8e5382516281b4a9e9f6f68e36d5f2d2bcaffa004c6a9f7872b6785c。
8. 失败构建任务已按保留期回收，未保留失败运行 Pod。新成功构建按既有 300 秒 TTL 回收，最终构建 namespace 中没有 Job/Pod；用户持久文件、数据库和对象不随清理销毁。最终工作空间接口没有异常 HTTP 响应。

- 一次性本地 PostgreSQL：12 通过，包含迁移和并发场景；没有在业务库执行并发测试。

- Postman 本地 HTTP 模拟：实际调用 Harbor 和 Kubernetes 计量适配器，验证原生无限配额、准确归属、PVC 完整库存，以及两种 503 故障被拒绝作为有效用量。模拟请求日志确认两个成员均被调用。

## 本轮发现并修复

新增后台后，原 platform_worker 账号 5 个连接不足，导致 plan worker readiness 失败。
核验受管角色后只上调预算至 16，各后台进程池限制为 1 常驻 + 1 溢出；
最终只读观测后台共 4 个连接，所有部署恢复就绪。没有改密码或重建业务数据库。

## 明确保留的范围

当前是分类计量与分类额度，尚无可挪用的统一硬配额。文件测试升级不扩大对象、镜像、
数据库或模型余额；真实支付、跨存储套餐调整、额外应用 PVC 创建、数据库硬字节限制、
备份恢复、回收站及持久的逐步构建/启动诊断仍需后续实施。写作/音乐仍待 Dify 集成。
MinIO 当前使用内部 HTTP；未新增公网入口。未验证原生未完成分片清理的实际延迟，
也没有设置完成对象/版本的自动过期删除规则。

私有原始截图、UI 结果与只读证据位于忽略的 release 目录，不提交登录态、密码或用户源码。
