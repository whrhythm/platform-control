# P1 AI 应用契约与实施记录

日期：2026-11-06。依据[产品纲领](product-charter.md)及[P1 实施清单](p1-delivery-plan.md)。

## 本批范围与状态

本批解决发布业务助手前必须确定的版本、身份、权限和调用兼容性。实现位于独立 `feature/p1-ai-apps` 分支；原工作目录中暂停的 HTML 预览改动保持原样。

**这是 P1-00 的实施记录，不是 P1 完成交付记录。** 本批契约尚未接入生产路由，无数据库迁移、镜像更新或公开入口变化。现有 LibreChat 原生 Agent 不会因新增这些契约就自动具备固定发布版本及代付能力。

## 归属与数据关系

| 记录 | 权威来源与关系 | 不允许的替代方式 |
| --- | --- | --- |
| 项目 | 控制面的 `WorkspaceProject`，归属已认证用户的个人环境 | 浏览器提交 namespace/owner 决定归属 |
| AI 应用绑定 | 一个项目一个主要业务助手；保存原生 Agent ID、绑定状态和创建请求 ID | 用同名 Agent 猜测绑定、自动合并旧 Projects |
| 原生 Agent | LibreChat 保存私人可编辑配置；创建权限、owner ACL 沿用原生机制 | 将可变 Agent 当前配置直接当成正式版本 |
| 草稿 | 修订号加配置摘要；任何指令、模型路由、知识索引、Skill 或工具变化改变摘要 | 改完配置仍沿用旧验收 |
| 试用记录 | 项目、草稿修订、摘要、测试会话、结果、确认者 | 模型一句“测试通过”作为用户确认 |
| 正式版本 | 不可变快照；线上版本指针独立于草稿及最后一次发布尝试 | 浏览器覆盖正式 prompt、模型或工具 |
| 会话 | 固定 actor、project、version、snapshot digest | 切换应用沿用旧对话、混入开发聊天 |
| 授权与预算 | 每次模型/工具调用重新读取当前状态 | 快照中保留旧授权即永远可访问 |

只有首次创建绑定可建立新的私人 Agent；已有项目、文件和应用不移动、不自动转型。绑定用服务端生成的稳定 ID 和持久操作意图协调两侧数据，不做隐式跨库事务。

## 输入与快照

可生成的定义见 `contracts/ai-applications.schema.json`，实现见 `control_plane/ai_application_contracts.py`。生成命令为 `python scripts/export_ai_application_contracts.py`。这些是内部契约，不是已发布的 OpenAPI 路由。

- 创建助手：`request_id`、`project_id`、固定首版模板；项目必须已归调用者所有。
- 更新草稿：`expected_revision` 与完整快照；服务器校验当前模型、知识、Skill 和工具权限后锁定更新。
- 发起对话：`session_id`、`request_id`、单条用户消息；历史消息从服务端该会话读取，拒绝客户端 owner/sponsor/system/tools/model 覆盖。
- 确认发布：幂等请求 ID、预期草稿修订与摘要、已通过的试用记录 ID。
- 快照：指令、明确模型及路由修订、输出上限、知识文件/索引摘要与授权引用、Skill 内容/修订、工具定义摘要及凭据引用。无明文密钥。

发布校验与保存必须在同一个草稿锁事务内完成。只通过纯函数校验不等于获得发布权限；适配层还必须验证当前账号、项目、模型、工具、预算及 ACL。

## 费用与权限

首版明确采用创建者承担费用：owner = sponsor，actor 可以是创建者或获邀请的使用者。actor 的身份和操作记录保留；使用者自己的赠额不能被误扣。团队代付和转移付费主体暂不支持。

`AccessFacts` 只允许由服务器从当前权威记录构造，并绑定 actor/project/version/sponsor。知识集合与工具授权集合必须已经按该应用及调用者筛选，不能把全局所有有效授权塞进集合。

`admit_call` 不返回或解密凭据，也不预占预算。真正的调用适配器还须：

1. 以 actor + session + request ID 记录唯一调用意图，同键不同消息拒绝。
2. 原子预占 sponsor 对应预算，防止并发超额；模型密钥仅留在服务端。
3. 将实际 actor、sponsor、project、version、用途关联模型消费记录。
4. 正常读取超时可重试；提交模型或写工具后结果不明，不自动重放，不声称未计费。
5. 工具执行时重新校验权限。凭据引用解析和目标范围检查不得只在进入聊天时完成。

上述持久调用意图、预算预占和代付接线是后续适配工作，当前纯函数测试不能替代它们。

## 绑定与故障状态约定

| 操作 | 正常状态 | 中断处理 |
| --- | --- | --- |
| 绑定 Agent | preparing → ready | 可核验失败为 failed；写结果未知为 verifying，按稳定 ID 查证，不盲目再建 |
| 更新知识 | uploaded → indexing → ready | failed 可显式重试；草稿索引失败不更改线上索引 |
| 模型调用 | accepted → running → succeeded | 明确失败 failed；写结果未知 uncertain；刷新仅查询同一调用 |
| 发布 | accepted → validating → active | failed 保留旧线上版本；写结果未知 verifying；审核/恢复留审计 |
| 停用 | enabled → disabled | 拒绝新调用，保留会话、资料及版本；运行中写操作依结果核验 |

清理失败任务不删除用户数据。被正式版本引用的知识索引不能按临时文件清理；撤销知识权限则立即拒绝后续检索，即使旧索引仍保留。

## 兼容性结论

- 当前模型代理能保留原生 Agent 的 `tools`、`tool_choice`、`tool_calls`、`tool_call_id`、工具结果和引用文本；已经用 HTTP 级合成依赖往返验证。
- 原生 `loadAgent` 读取当前可修改记录。固定发布必须增加服务端版本解析，不能仅把 release ID 换成原生 agent ID。
- 已部署 LiteLLM 用户 key 归当前登录用户；受邀者使用创建者预算还没有接线，不开放分享来代替这一实现。
- 当前真实环境未配置 RAG API/嵌入模型。已有文件搜索开关不代表检索已可用；P1-02 需独立部署与核验。
- 用户工具选择和平台审核目录仍需统一授权适配，不能直接继承原生所有可选工具。

- 合成测试覆盖：发布配置不可被客户端覆盖；会话跨用户/项目/版本拒绝；权限撤销；旧索引不继承新授权；草稿变动使确认失效；调用者与付款者分离；上游错误不泄露、不重发；工具结果与引用往返。
- 真实 UI：指定验收账号成功创建私人测试 Agent `P1链路验收-20261106`，通过原生产品会话入口发送一次合成计算需求。聊天显示实际工具命令 `python3 -c "print(19 * 23)"`、stdout `437`，随后流式回答“真实结果为 437。”；刷新后命令输出、最终回复和自动生成的会话标题保留。

## 后续适配决策

1. 项目创建先在控制面持久化绑定意图，生成确定的私人 Agent ID；LibreChat 服务端按该 ID 查证/创建，校验 owner 并补齐原生 ACL 后回执。重复请求不能调用当前每次随机生成新 Agent ID 的浏览器创建接口作为幂等实现。
2. 业务助手试用与正式会话继续使用原生 Agent 的执行与流式组件，但通过服务器加载指定快照；不接收浏览器的 `ephemeralAgent`、`promptPrefix` 或模型/工具覆盖。普通聊天和 OpenHands 开发会话保持现有行为。
3. 创建者试用可以沿用已有个人模型身份。受邀用户正式调用必须先完成 sponsor 适配和独立身份测试；不能先开放原生分享，再声称实现了应用交付。
4. 知识读取使用专属、明确选择的集合，不把整块个人磁盘加入检索。先部署真实兼容 RAG 和嵌入服务，再显示“知识可用”。
