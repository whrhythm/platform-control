# CodeChat 产品完善与分阶段实施方案

日期：2026-11-02。入口以 LibreChat 为主，平台控制面承担管理员、权益、资源编排与审计。本文是设计与实施顺序，不表示所有能力已上线；具体上线事实记录在验收文档。

## 1. 产品界面与文件操作

主界面始终保留聊天。左侧“我的空间”展示个人文件，文件行提供预览、下载、编辑、删除图标，并具有文字提示和键盘可访问名称。预览使用浮窗；文本编辑从最右侧展开。文件区和应用管理后续拆分为清晰的“文件”和“应用”入口，不再把所有操作塞进一张文件列表。

上传和 Agent 生成的文件使用同一套接口，没有“上传文件可以管理、生成文件只能下载”的区别。

- 第一阶段支持 UTF-8 文本/代码编辑、纯文本预览和 PNG/JPEG/GIF/WebP 图片预览。不执行 HTML、SVG、脚本或用户 Markdown 中的任意 HTML；PDF/Office/音视频等格式后续逐项接入，当前提供下载。
- 编辑加载实际文件和版本标记。保存和删除需提供该版本；发现已改变时返回冲突，保留编辑内容，提示重新加载。关闭未保存编辑需要确认。
- 版本检查可发现已发生的 Agent 修改，但文件系统没有与任意第三方进程协作的原子“比较后替换”。第一阶段不承诺抵御所有并发时序。后续统一 Agent 文件写入网关或按工程协调写锁，再提供严格并发保证。
- 删除先确认具体文件，普通界面不提供不经确认的递归删除。文件删除是永久操作，应明确提醒备份；后续增加回收站、保留期和恢复功能，回收站占用也计量。
- 停止应用、构建失败、套餐到期都不等于删除文件；销毁个人空间与删除应用是不同权限、不同确认流程。

接口约定：文件 GET 返回 ETag；编辑 PUT 使用 overwrite=true 与 If-Match；DELETE 要求 If-Match，只有普通文件可以删除。版本冲突返回 409，容量不足返回 507。预览大小在 librechat.yaml 的 codechat.filePreviewMaxBytes 配置，默认 1 MiB，最大不超过现有单次传输上限 16 MiB。

## 2. 构建、部署与用户反馈

编程对话提交后台发布任务后结束，界面继续观察任务，不能一直等待模型轮询。任务阶段为：排队 → 准备 → 构建 → 推送核验 → 部署 → 入口就绪 → 运行。

失败必须告诉用户：哪个工程、失败阶段、当前版本是否可用、文件是否保留、临时资源是否仍在清理、下一步能否重试。

- 文件面板关闭时仍观察应用状态，阶段变为失败时发出通知，并保留失败入口。
- 应用详情区解释构建失败、镜像核验失败和启动失败，提供修复后显式重试；状态不明或需要管理员处理时不能无限重试。
- 清理状态单独显示 pending/complete；发布失败记录不会因为清理 Pod 而丢失。
- 已有可用版本时，新版本失败应保留或恢复上次可用镜像，提供旧版本地址；不允许为了清理失败发布而关闭原来正常的业务。
- 后续增加持久任务中心、按任务的构建步骤与脱敏诊断、用户取消、日志保留策略。不能把原始平台异常、凭据或全部环境变量直接显示给用户。

## 3. 总空间应是逻辑账户

用户看到“总空间”，实现上采用统一额度账本和多个存储适配器。Kubernetes PVC 只是文件盘和应用数据盘的承载方式，不能代表 PostgreSQL、MinIO 或 Harbor 的用量。

建议计量：

```text
实际使用量 = 个人文件与工程虚拟环境
           + 个人依赖缓存和 Agent 持久状态
           + 该用户所有项目数据库的实际大小
           + 对象与保留版本/回收站的大小
           + 私有镜像的归属用量
           + 应用持久数据盘的归属用量
```

相同底层数据只能计一次。例如应用挂载的目录已经属于个人文件盘，不再按另一张“应用盘”重复收费；虚拟环境和 wheel 缓存是两份实际存在的文件，可以分别占空间。镜像构建中下载并打包的依赖属于镜像内容，不再额外按“下载流量大小”算成持久文件。

共享基础镜像、平台服务、数据库 WAL/副本、Longhorn 副本和平台备份开销，属于基础设施成本，第一版不混入用户文件用量。镜像共享层由明确的归属规则计量；不能直接把整个 Harbor 项目的数值与同一批层的大小重复相加。

构建临时文件、临时 Pod 和 tmpfs 不是长期持久空间，应设置并发、运行时长和临时存储上限；执行前预留预算，结束回收。若以后收费，以单独公开的计算/临时存储规则计费。

### 3.1 额度和底层容量分开

账本需要区分：套餐总额度、分项预算、实际使用、进行中预留、观测时间、完整性和异常。不可用数据返回 unknown/stale，不能当作零。

第一版采用可解释的分项预算，例如 20 GiB 套餐分为文件盘 12 GiB、数据库 2 GiB、对象 4 GiB、镜像 2 GiB；分项上限总和不超过套餐。显示实际使用与分项额度，用户申请调整预算或升级。

普通用户只需选择套餐、查看总量和用量明细。分项预算由平台按项目需求自动安排，不要求用户理解 PVC、数据库 tablespace 或手工配置配额；运维仍可从管理端查看预算与底层容量。资源不足时提供业务层面的释放空间或升级提示。

这比允许各存储组件分别吃满整个总额度更可控。不能声称多个异步采样的独立存储系统天然拥有精确、原子的统一硬限额。

PVC 可以在存储类和驱动支持时扩容，通常不能原地缩容。因此第一版不承诺已给文件盘分配的容量能任意缩回去转给数据库；这种调整可能需要显式迁移。现有用户磁盘不因引入新账本被自动缩小或删除。

当前首先显示**个人磁盘用量**：扫描同一工作卷里的 files、agent 状态和依赖缓存，展示时间和可用空间；数据库、对象及镜像尚未接入统一统计时，界面必须明确说明。这不是完整总量账本。

### 3.2 Python 依赖

工程依赖放在工程自己的 .venv；pip、uv、npm 缓存放在该用户的持久卷。执行器和共享基础镜像预装的通用运行库不向每个用户重复计量。禁止把用户项目依赖安装进平台执行器自身的系统环境。

容量不足时仍允许读、下载、备份和释放空间；限制新的写入、构建和新增应用。到期和升级失败不得触发数据自动清空。

## 4. 套餐、等级与测试付费

“用户等级”由套餐权益决定，不由 LibreChat 前端的标签或用户自报角色决定。建议先区分：试用、基础、专业；明确存储总额、应用数、同时运行数、编程/构建并发、单任务资源和模型额度。管理员权限与付费等级无关。

首轮不确定真实售价，使用管理员配置的测试套餐和测试订单；现有默认 2 GiB 及应用数不能被前端价格卡片悄悄改写。升级时展示权益差异、当前占用和扩容准备状态。

```text
用户选择套餐
  → 服务端生成带价格/权益版本快照的订单
  → 测试支付适配器确认（明确“测试”，不真实扣款）
  → 幂等记录订单结果
  → 权益变更任务
  → 更新预算、扩容底层存储及各服务限额
  → 观察真实开通结果
  → 新权益生效或明确显示等待/失败
```

订单已确认与资源已准备是两个状态。不能只在数据库把 2 改成 20，就告诉用户磁盘已经扩大。扩容失败时保留原数据和原有可用权益，管理员可重试；真实支付以后再接入验签、退款和对账。

需要的记录：PlanVersion、Subscription、Order、PaymentEvent、EntitlementChange、QuotaBudget、UsageSnapshot、QuotaReservation。以 issuer/subject 或平台稳定用户 ID 关联，禁止按可修改邮箱作为账本主键。

首次注册赠送的 1 美元模型额度与存储套餐分开记录，一人一次；重新登录、升级、重复支付通知不能重复赠送。LiteLLM 是模型调用额度执行器，不是整个平台的订阅和存储账本。

降级时若现有预算或实际用量不满足新套餐，先拒绝立即降级或提示处理；不缩容 PVC，不删数据库，不删除超额项目。到期宽限、限制新增操作、数据保留与最终销毁分别制定规则。

测试至少覆盖重复支付事件、乱序事件、订单归属、客户端伪造金额、并发升级、扩容失败、退款后不能多次加额度、到期保留数据。现有测试订单仅控制项目权益，不能直接冒充上述订阅实现。

## 5. Coding、写作与制作音乐

采用“任务能力”入口，而不是把 OpenHands 当成面向用户的模型名称。

| 能力 | 后端路由 | 当前计划 |
| --- | --- | --- |
| 普通聊天 | LiteLLM 模型 | 保持现有能力 |
| Coding | 平台编程网关 → OpenHands SDK → 个人工作区 | 优先改造 |
| 写作 | 可配置写作 Agent 或 Dify 工作流 | Dify 未部署前不伪装成可用 |
| 制作音乐 | 后续音乐工作流/服务 | 待实现 |

标签不是多选工具开关；第一版同一条消息只选择一个主能力。模型配置成为该能力内部的可选高级设置。路由在服务端验证，只允许管理员配置的能力与端点；前端不提交任意目标 URL。

### 5.1 切换不丢上下文

平台 conversation_id 保持不变，每条消息记录 capability_id、执行器、任务 ID 和结果引用。切换只影响下一条消息，不修改已经运行的任务；任务执行中禁用切换或明确排到下一轮。

已有 OpenHands 聊天兼容映射为 Coding 能力，保留原消息、工程和磁盘，不要求重新注册或重新建空间。路由改造需要显式处理旧消息和仍在进行的任务，不能一次性改名导致旧聊天无法继续。

交接内容包括：当前用户目标、已确认约束、相关聊天历史/摘要、最新用户指令、当前工程及必要文件引用、已有应用/发布任务结果。不能只把切换后的第一句话发给新执行器，也不能把平台密钥和全部工程文件无差别塞进上下文。

Dify 的会话 ID 是外部执行器会话，不是平台聊天 ID；按用户、平台聊天、能力和工作流版本映射。Dify/Agent 自身记忆不能覆盖平台聊天记录。长对话使用可追溯摘要加近期消息，保留原始聊天；所有能力回传文件和交付物仍关联同一用户空间。

验收：普通聊天确认三项要求 → 切到 Coding 按三项要求生成代码 → 切到写作结合项目内容写说明 → 切回 Coding 修改代码；刷新/重新登录后仍保持聊天、能力选择和工程引用。Dify 未就绪时禁止用另一个模型静默替代并声称工作流完成。

## 6. 共享 PostgreSQL

复用共享 PostgreSQL 集群，按项目建立独立数据库及受限角色，而不是把多个用户的表全部放进一个不受控 public schema。一个用户拥有多个项目数据库，用量汇总到该用户账本；数据库连接信息由平台注入相关工作环境和应用。

通过 pg_database_size 采样数据库本体大小，包含表、索引等；平台 WAL、备份和副本不简单归到某个用户。不把“数据库已申请”当作已能连接，也不在普通界面展示共享管理员凭据。

特别限制：标准 PostgreSQL 没有“给每个数据库设置精确字节硬容量”的通用内置设置。采样、申请预留、禁止新增数据库与写入限制是软限额策略，不能阻止任意直连写入在采样之间超额。需要水位预留和告警；若要求严格硬限额，需要验证兼容的配额扩展或调整数据库承载方案，不能靠一条 SQL 或轮询器伪装硬隔离。

项目数据库默认随应用停止保留。删除应用不删除数据库；删除数据库需要另行确认、备份和保留期。迁移、备份、恢复、连接池和迁移权限是开通前的验收项。

## 7. 失败、取消和资源回收

任务记录、临时计算、业务运行资源、持久用户数据采用不同生命周期。

| 场景 | 回收动作 | 必须保留 |
| --- | --- | --- |
| 构建失败/超时 | 终止并回收该任务 Job/Pod，随 ownerReference 回收临时凭据；释放预留 | 源码、失败任务与必要诊断 |
| 首次部署失败 | 停止该失败部署的计算，避免无限 CrashLoop；回收相关构建任务 | 个人磁盘、任务状态、私有镜像按保留规则处理 |
| 已有应用的新版本失败 | 保留或恢复上个可用版本，回收失败版本的计算 | 上个版本及用户数据 |
| 用户取消 | 发出取消，观察停止，再回收临时资源；禁止自动重试 | 已生成文件和取消记录 |
| 删除应用 | 确认后回收应用运行资源，保留个人盘、数据库和对象数据 | 用户持久资料 |
| 销毁个人空间 | 单独授权、备份/保留期、最终确认后执行 | 审计及法定/产品保留资料 |

控制器操作只针对任务日志记录的 UID 和归属，不能按名称前缀批量清空 namespace。删除失败持续重试并展示清理待处理，不提前显示“已清理”。控制器重启后从持久记录恢复；新任务不能被旧任务迟到的观察结果覆盖。

构建 Job 使用 activeDeadlineSeconds 和 ttlSecondsAfterFinished 作为兜底；正常路径先保存业务结果再回收。仅依靠 TTL 不能完成应用 Deployment、PVC、数据库、对象和镜像的生命周期管理。失败重试必须由用户明确发起，清理未完成前不开始新版本。

## 8. 实施顺序与验收

| 阶段 | 交付 | 通过标准 |
| --- | --- | --- |
| A，当前推进 | 文件预览/编辑/删除、个人磁盘用量、失败通知与回收、旧版本保护 | 真实用户界面操作；版本冲突不覆盖文件；失败后无无限运行的构建/失败应用 Pod；上次可用服务保留 |
| B | 能力标签、同一聊天上下文交接、文件/应用入口分离 | 不依赖用户去模型列表寻找 OpenHands；跨能力切换与刷新均保留上下文；未实现能力明确不可用 |
| C | 统一额度账本、套餐与测试升级、文件盘扩容 | 测试支付幂等；权益与实际存储观察一致；用量不可用不显示零；升级保留原文件 |
| D | PostgreSQL/MinIO、镜像与应用持久盘的分项计量 | 实际连接隔离、写入/读回、计量归属、容量阈值、备份恢复和独立销毁验收 |
| E | Dify 写作/音乐等能力、真实支付与运营 | 工作流结果和账单对账真实验证后再开放 |

当前新增代码属于 A。B–E 不能仅凭本文列为已完成；真实价格、生产支付和数据销毁策略需要在实施时形成可审阅的配置与验收。

## 9. 补充建议

增加版本历史/回滚、任务中心、清理异常告警、可下载用量明细、数据导出与备份恢复。为项目、文件、应用、数据库分配稳定标识，避免用户改名造成归属丢失。所有后台操作提供幂等键、阶段和取消语义。

优先保护最后一次成功交付与用户资料。平台整体物理磁盘、Longhorn 快照、Harbor 保留层、PostgreSQL WAL 和节点可分配资源需要另有运维水位；出售逻辑额度不能忽视单节点的实际承载能力。
