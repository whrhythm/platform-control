# 星桥产品纲领与阶段交付标准

版本：1.0。生效日期：2026-11-06。适用于产品设计、代码开发、测试、部署和商业试点。

本文是后续产品工作的统一基准。核心决策已由用户确认：以可交付、可持续运行的 AI 应用为定位，以对话驱动开发为创建方式。本文规定目标和验收标准，不把目标写成已上线能力。后续用户的明确决定优先；既有技术契约、数据保护与权限要求继续有效。

## 1 产品承诺

**帮助个人与小团队通过对话，把业务需求变成具有知识、工具和执行能力的 AI 应用；试用验证后交给团队或客户使用，并持续改进。**

用户购买的是任务完成质量、交付效率和持续使用的确定性。模型、Agent、文件空间和运行资源是实现这一价值的支撑，不是需要用户自己拼装的产品。

完整生命周期固定为：**创建 → 试用 → 修改 → 发布 → 持续维护**。任何阶段的设计都必须回答：用户要完成什么、当前发生了什么、结果在哪里、下一步能做什么、需要承担什么费用。

产品不以按钮数量、接入组件数量、代码量、模型自称完成或一次演示成功衡量进展。

## 2 服务谁以及先解决什么

| 角色 | 核心需求 | 默认能力边界 |
| --- | --- | --- |
| 应用创建者 | 熟悉业务但不愿承担完整开发与运维，通过对话完成一个实用 AI 应用 | 管理自己的项目、知识、工具授权、版本、访问范围与预算 |
| 应用使用者 | 向已发布应用提问或交办任务，得到可信回答和可核验结果 | 使用被授权的应用，不默认看到源码、开发聊天、系统指令或密钥 |
| 团队购买者 | 确认业务价值、持续费用、成员访问和数据可控 | 了解账单与权益，不因付款自动获得跨团队权限 |
| 平台管理员 | 处理用户、套餐、模型、工具审核、异常与运营 | 在 Platform Control 操作；敏感操作有依据、权限和审计 |

首批目标是有重复知识问答和业务操作需求的小团队。售后/内部支持是切入假设，须由真实访谈和试用验证，不宣称已经验证付费意愿。

首发样板为**售后 AI 助手**：依据获授权的售后资料回答问题，必要时创建或查询工单，说明实际处理结果；配套工单页面用于查看和处理记录。已有工单网页是基础资产，不等于这一 AI 助手已完成。

首发不承接关键交易、强监管敏感数据、复杂企业定制或未经验证的全天候服务承诺。正式接收真实客户数据之前须通过数据保护门槛。

## 3 产品边界与扩展规则

### 应当做

- LLM 对话、可配置的业务 Agent、知识检索、授权工具调用以及结果反馈。
- 为 AI 应用补齐必要的页面、API、文件和持久业务数据；可用编程助手创建和修改这些配套能力。
- 应用的测试、版本发布、访问控制、用量、反馈、运行维护与退出导出。
- 普通用户可直接完成主要任务；模型、system prompt、工具、Skill、检索参数等在合适的进阶入口可配置。

### 近期不做

- 万能低代码搭建器、通用商城/ERP 工厂、游戏开发平台，以及与主场景无关的写作和音乐入口。
- 同时接入多个工作流引擎、公共模板/组件交易市场、自动选模型优化、复杂分支合并或大规模企业定制。
- 为展示某项组件能力而增加独立产品入口，或要求用户先理解全部底层术语。

HTML、小游戏和纯网页可以作为回归测试样本，不能成为产品定位或整体验收的替代品。也不承诺任意语言、框架、数据库或工程都能即时预览和部署。

引入 Langflow、Dify 等组件前，先记录当前用户任务的具体缺口、既有能力为何不能满足、接入成本、权限与计费影响、退出方案及可测验收条件。只有确实缩短主流程或改善质量时才进入排期；组件选择不是产品阶段。

## 4 核心概念不能混淆

| 概念 | 产品含义 |
| --- | --- |
| 项目 | 一个持续业务目标，关联开发对话、文件、配置、知识、测试和发布记录；首版维护一个主要 AI 应用 |
| 开发助手 | 帮创建者实现需求的 Agent，现有 OpenHands 属于此角色；默认不向最终应用使用者开放 |
| 业务 Agent | 已交付应用中的任务执行者，依据发布版本的行为、知识和授权工具工作 |
| Skill | 可复用、有版本的任务指导或操作方法；绑定 Skill 本身不能授予工具、文件或外部系统权限 |
| 工具 | 具有明确输入、输出、权限和副作用的能力；MCP 是接入方式之一，不等于自动可信 |
| 知识库 | 经授权导入、索引、检索和更新的资料；与普通工程文件区分，权限需贯穿检索与回答 |
| 草稿 | 创建者正在修改的代码与 AI 行为配置，不自动影响线上版本 |
| 试用环境 | 对指定草稿进行对话或页面验证的环境，明确数据和工具操作范围 |
| 发布版本 | 已确认的代码/镜像、Agent 指令、模型配置、Skill、知识索引版本与工具权限配置的可追溯组合 |
| 应用使用会话 | 最终用户与已发布应用的对话，不能混入创建者开发聊天或其他用户会话 |

发布记录保存凭据引用和授权范围，不复制明文密钥。模型名称或别名不保证供应商行为永久不变；应记录实际调用模型与路由变化，并在变更后回归验证，不宣称外部模型完全可重现。

用户个人空间是持久资产的载体，项目归属和隔离由服务端保证。它不等于某个容器、某一份 PVC 或一次聊天。一个用户可以有多个项目；普通聊天不必创建项目。已发布应用的最终用户不能默认继承创建者的开发环境权限。

## 5 五个阶段的完整体验

| 阶段 | 用户动作 | 必须交付的体验与结果 |
| --- | --- | --- |
| 创建 | 描述业务目标、提供资料，选择必要能力 | 明确服务谁、解决什么、怎样验收；自动带入合理默认值，只追问影响结果的必要问题 |
| 试用 | 测试对话、操作配套页面，查看回答依据和工具结果 | 聊天成果旁有明显的“打开预览”；显示当前草稿与测试数据范围；真正能交互，失败有原因 |
| 修改 | 通过聊天提出变化，必要时直接编辑或调进阶参数 | 沿用项目上下文，给出改动摘要；刷新或更新后验证新效果，不能把旧预览显示为新结果 |
| 发布 | 确认版本、访问对象、费用承担与数据影响 | 发布已验证版本；显示进度、地址和最终状态；代码或配置变化后旧确认失效 |
| 持续维护 | 查看使用反馈、异常与费用，再改进版本 | 新修改先进入草稿，原发布版本继续服务；可暂停、恢复、导出和受控删除；数据保留规则明确 |

### 试用必须真实而有边界

对话型应用提供真正的测试会话；有配套页面和后端的应用，启动首发支持范围内的实际服务。静态页面展示不代表后端、数据库和工具链已经运行。

测试会话使用独立的测试数据范围；有外部副作用的工具默认不调用生产写接口。若无可用测试环境，明确标记不可完整试用或在具备权限的情况下要求一次具体操作确认，不能用模拟结果冒充真实执行。

预览应区分加载、启动、就绪、更新、失败和已停止。闲置停止只回收相应运行资源，不删除持久文件和业务记录；重开后说明哪些临时测试状态不会保留。

### 上下文必须可理解

项目切换时显式切换文件、知识、工具与运行对象；不同项目或不同用户不能意外共享上下文。普通聊天转入项目时允许用户选择相关内容，不默认把全部历史、附件和密钥传入 Agent。开发会话不自动成为已发布应用的知识库。

### 界面为任务服务

保持聊天主界面稳定，以项目名称、草稿/线上状态和少量明确动作提供方向。文件、代码、工具细节和日志按需展开；不能同时堆满文件树、部署卡片和监控面板。模型与进阶设置可达，不强迫普通用户先配置 Agent 才能开始。

“打开预览”“继续修改”“确认发布”“访问应用”要易于发现。安全地重试、取消、查看费用和导出均保留直接操作，不强迫所有动作通过聊天。中文、亮暗主题、窄屏和键盘可用性属于验收范围。

## 6 不得牺牲的产品规则

1. **真实反馈。** 流式展示可公开的回答和实际执行进度，重复工具信息折叠；不展示模型私密推理，不以假进度或循环动画掩盖停滞。
2. **明确失败。** 说明已完成什么、未完成什么、线上服务和数据是否受影响、用户下一步能做什么。原始日志是补充，不是唯一反馈。
3. **有限执行。** 自动修复、模型调用和工具执行都有时间、次数、并发与预算边界；耗尽后保留成果并停止，不无限循环消耗。
4. **状态可信。** 普通查询超时保留上次确认状态并重试；写操作结果不明先核验，不能直接重放或伪称失败。刷新/断线不能重复创建任务、订单或发布。
5. **版本一致。** 试用结论绑定对应版本；发布同时检查代码与 AI 行为配置变化。不能只核对源码而漏掉 prompt、知识、模型或工具权限改变。
6. **数据持久。** 任务失败、停止服务、删除聊天或套餐到期都不等于授权删除数据。删除须说明范围、依赖、保留期和后果，并确认实际清理结果。
7. **恢复有边界。** 源码恢复、应用版本回退和业务数据恢复分开处理。新版本失败尽量保留旧版本；不兼容的数据变更须有明确迁移及恢复方案。
8. **权限贯穿。** 身份、文件、检索、工具调用、发布、应用访问与账单均在服务端校验；界面隐藏不构成授权。工具返回和知识文档都是不可信输入，不能自行扩大权限。
9. **成本可解释。** 开发、试用、线上应用调用和运行消耗可区分、可归属。模型额度不足与磁盘不足分别说明，不用一个模糊的余额替代所有权益。
10. **可退出。** 提供首发承诺范围内的配置、源码和业务数据导出；说明不能导出的第三方依赖及迁移步骤，不承诺所有应用完全离线可用。

## 7 从功能到商业应用的推进顺序

以下是有先后依赖的阶段门槛，不是工期承诺。访谈可与工程修复并行；产品团队未通过阶段评审，不把下一阶段目标当作已完成。

| 阶段 | 核心问题 | 必须完成 | 退出门槛 |
| --- | --- | --- | --- |
| P0 现状与范围对齐 | 已有能力究竟能支撑什么 | 盘点代码、部署、UI 和验收证据；确认首发支持矩阵、项目/Agent/会话关系、复用与缺口；整理原型 | 每项承诺有实现位置或明确缺口，首发业务脚本和验收方式确定；不再以组件已部署认定功能完成 |
| P1 首个 AI 应用闭环 | 用户能否独立交付一个知识助手 | 创建项目、导入授权资料、测试回答与依据、修改行为、发布给受邀用户、回到草稿迭代；包含失败和刷新恢复 | 重复完成五阶段流程；最终使用者无需进入开发界面；缺失知识、越权检索、版本切换均有正确结果 |
| P2 从回答到办事 | 助手能否正确执行实际业务 | 在 P1 上增加创建/查询工单工具、必要的工单页面与存储；权限、确认、幂等与真实结果反馈 | 售后 AI 助手完整任务验收通过；重复提交不重复建单，未授权用户不可查他人工单；修改发布后原记录保留 |
| P3 可持续使用的内测版 | 用户回来后是否还能放心使用 | 项目状态、线上反馈、用量预算、异常恢复、版本回退边界、导出和运维处理流程 | 达到第 8 节内测门槛；真实数据前完成独立备份恢复；用户可以不依赖开发者后台修补完成任务 |
| P4 受控商业试点 | 有人愿意付费且平台能履约吗 | 明确套餐、真实支付与权益到账、对账退款、访问与数据条款、支持渠道；邀请小规模同场景团队 | 真实付款和财务核对完成；试点观察到持续任务使用、返回修改及可解释的成本；阻塞问题有处置和退出方案 |
| P5 扩大商业应用 | 能否可预测地服务更多客户 | 根据留存与成本优化引导、支持和容量；逐步增加相邻场景或团队能力 | 达到试点评审确定的留存、毛利、支持负担和容量指标，再扩大范围；不得凭演示成功直接扩张 |

P1 是 P2 的一个可独立验收的纵向切片，不是先做一个没有发布和维护能力的配置页面。已有工单能力可以复用，但不能跳过 AI 回答、知识权限和最终用户访问验证。P0 若发现已有能力足够，可用证据直接通过对应条目，无须重复造轮子。

## 8 质量门槛和证据

以下数值是首版的**内部验收目标**，不是行业标准、线上实测成绩或 SLA。P0 固定测量方式及负载条件；若因实测需调整，须在测试前记录理由和影响，不得失败后悄悄降低门槛。

| 维度 | 内测目标 | 记录方式 |
| --- | --- | --- |
| 请求反馈 | 点击提交后 1 秒内出现已受理、校验失败或明确的连接状态 | 记录从用户操作到界面反馈的时间，不把已受理算作模型回答 |
| 模型交互 | 已就绪环境的普通测试对话，首次有意义回答 p95 不超过 10 秒 | 单列排队、冷启动、检索与模型等待；失败/超时不从样本中隐藏 |
| 执行透明 | 超过 10 秒未获得新进展时解释正在等待什么；到任务期限必须终结或进入明确核验状态 | 不伪造进展，不要求每 10 秒必须产生一条工具输出 |
| 核心交付 | 每条已承诺场景先连续 3 轮完整成功，再积累至少 20 次完整尝试，成功至少 19 次 | 覆盖至少 3 个独立测试身份、2 个测试日；记录失败和所有人工干预，修复后重新回归 |
| 业务正确性 | 固定关键用例全部通过：依据回答、无依据说明、授权工具、工单持久化与查询、版本生效 | AI 自评不能代替确定性断言和人工业务判断；RAG 答案正确性、引用支持性与无答案情形分别计分 |
| 重要保护 | 越权访问、重复扣费、重复业务写入、数据误删与版本错发用例必须全部通过 | 发现任一问题阻止相应试点，不用平均成功率抵消 |
| 无协助使用 | 至少 3 位目标用户各自完成首次使用及一次返回修改，无开发者后台修补 | 记录需要解释的位置、放弃原因与耗时；访谈口头认可不算完成 |

测试身份只能使用当前已授权账号或专门获批的测试身份。当前只有一个指定验收账号可做用户流程时，先完成其回归，多身份门槛标记“未满足”；不得擅自使用其他真实账号，也不得宣称通过。

20 次尝试仅提供小样本回归证据，不能证明生产 95% 可用性。复杂生成、构建和预览冷启动单独报告 p50/p95、超时率和重试费用；P0 为支持矩阵中的场景设定期限，不承诺所有项目统一秒开。

固定异常矩阵至少包括：模型超时/限流/额度不足、知识索引失败、工具超时与未知写入结果、预览启动失败、构建失败、部署未就绪、浏览器刷新/断线、重复点击、容量不足、权限撤销、修改后重新发布及运行环境重启。检查是否保留成果、重复执行、影响旧版本和完成清理。

每次验收记录：代码与镜像版本、环境和账号类型、场景与输入数据、操作步骤、预期/实际结果、耗时、用量、失败次数、人工干预、证据位置和遗留问题。凭据、私人对话及真实客户数据不写入报告。

## 9 商业与运营原则

### 收费对象与价值

优先向创建并维护应用的个人/团队收费；受邀使用者默认无需购买创建套餐。首版线上应用模型调用由应用所属账户承担并显示归属；若未来支持使用者自带额度或转付费，必须单独设计告知、授权和防重复扣费。

套餐分别说明模型费用额度、持久存储、运行规格、可发布应用数、并发与执行限制、访问与支持能力，以及有效期。模型价格不同，不用固定 Token 数冒充精确的消费额度；如展示 Token 估算，标明模型和估算口径。

人民币售价、授予用户的模型预算、LiteLLM 美元计量、平台供应商实际成本是不同概念。例如售价 10 元、模型预算折合 5 元，不能显示成给用户充值了 10 元模型额度。订单固定成交权益和折算规则；目录改价不追溯改写已成交订单。注册赠额沿用有效配置，发放必须幂等，不能因升级或重新登录重复赠送。

### 从模拟交易到真实交易

虎皮椒 V3 本地模拟器是接口与故障测试工具，不能作为真实支付验收证据。真实收费前验证服务端金额与签名、重复/乱序/延迟通知、订单查询核验、权益开通重试、到账对账、退款与权益处理、过期和欠费处置。客户端跳转成功不代表支付成功，支付成功也不代表资源已经开通。

测试订单不能混入实际收入。真实交易试点需商户条件、明确费用授权及相应用户确认；不能把历史的模拟支付授权扩大为任意真实扣款授权。

### 真实数据与公开服务

当前单节点、本地恢复演练和内部域名访问不能证明生产高可用、公网可用或整机故障可恢复。客户真实数据试点前，必须有独立于集群主机的备份目标、明确恢复点/恢复时间目标及演练证据。缺少条件时保持合成数据内测，不用文本承诺替代。

公开服务前完成适用的身份与滥用防护、TLS/域名访问、知识与工具权限、密钥保护、数据保留与删除规则、隐私告知和支持流程。具体商业/法律条款在真实经营范围确定后专项核验，本文不代替该审查。

### 市场验证

试点重点观察：首次独立交付率、首次价值时间、每周实际完成任务的应用数、创建者返回修改、最终用户持续使用、真实付费与续费、模型和运行成本、退款及每客户支持耗时。

不以注册数、累计聊天数或一次性满意评价代替价值验证。试点前固定观察周期与继续/停止条件；访谈、真实费用授权和商业判断由产品负责人参与，AI 不能编造客户意见或代替购买意愿。

## 10 后续 AI 的执行协议

### 每次任务开始前

1. 阅读本文及相关仓库 AGENTS.md，确认当前阶段与用户最新指示；用户尚在讨论时不自行恢复编码。
2. 检查当前代码、未提交改动与相关验收记录，区分计划、实现、部署和真实使用四种状态。
3. 用一句话写清本次改善哪类用户的哪段完整任务；列本次范围、暂不做的内容、依赖和可观察的通过条件。
4. 优先复用已有身份、项目、权限、用量与发布机制；不要为一个 UI 入口另造一套任务或计费系统。

### 开发和测试时

- 按纵向用户任务交付，不能只完成后台接口或一个配置页就称为产品完成。
- 每项改动同时检查普通用户入口、管理员职责、费用归属、权限、持久数据、失败/取消/重试/恢复和已有项目兼容性。
- 后端以 Python/Go 独立服务承载业务，浏览器为主。未来 Tauri 仅承担 GUI 和独立 Sidecar 生命周期，不把复杂业务塞进 Rust 主进程。
- 新能力先说明技术契约、状态与迁移影响，再实施；保留既有安全与租户边界，不因赶功能移除。
- 自动化测试可以用脚本；交付验收必须覆盖真实产品 UI。直接改数据库、绕过界面或人工补资源只能用于明确诊断/修复并记录，不能算“用户独立跑通”。
- 不覆盖用户工程与其他未提交工作，不擅自删除数据，不通过未经批准的账号扩大测试。
- 不声称底层组件支持某能力就等于本产品支持；必须验证接入后的权限、成本、错误处理和实际结果。

### 每次交付后

按以下格式简要记录并报告：

```text
产品阶段与本次用户任务：
用户可见变化及入口：
实现 / 已部署 / 已通过真实 UI 验收的范围：
测试版本、环境、轮次、结果与证据：
人工干预、失败及尚未通过的门槛：
数据、权限、计费与兼容性影响：
下一步唯一最高优先级任务及依赖：
```

若主流程未通过，优先解决断点，不转去扩展新功能。没有证据不能写“完成”“稳定”“生产可用”；模拟器、单元测试、单账号 UI 成功、真实客户试点分别陈述。

### 方向变更

新增主场景、改变收费对象、扩大公开范围或引入新的核心平台，属于产品决策。先给出用户价值、代价、替代方案和验收方式，再取得明确方向并更新本文。普通实现细节由开发者在已授权范围内判断，不反复要求用户审批。
