# 星桥产品定位与体验设计

历史设计日期：2026-11-06；状态说明更新：2026-11-07。本文保留早期业务工具体验的演进记录，不再作为当前产品设计基准。当前以[产品纲领](product-charter.md)、[总体设计](overall-design.md)和[交付计划](p1-delivery-plan.md)为准；售后工单只是验收样板。自动开发工具、管理员审核、用户授权与联合发布见总体设计。用户已授权按左侧统一管理方案恢复改造，当前证据见[左侧项目工作区](p1-project-sidebar.md)；下述目标体验不代表已经上线。

星桥面向有明确业务需求、缺少开发资源的小团队，帮助他们通过对话创建、维护和分享业务工具。产品承诺是：**把每天重复的业务工作，变成团队用得起来的小应用。**

近期以“小团队内部售后工单”为首个验证场景。先证明一类用户能完成业务、愿意持续使用和付费，再扩展场景。它是待验证的切入点，不是已有客户需求结论。

## 1 产品判断与商业边界

现有平台已有聊天编程、文件管理、构建发布、用量权益、审批与部分恢复能力，说明核心链路具备继续打磨的基础。它仍是功能原型：一次演示跑通，不等于客户可以独立完成任务，更不等于已验证商业需求。

“说出需求，得到在线链接”应当成为演示重点，但不能宣称是独有能力。[Replit 提供应用发布](https://docs.replit.com/learn/projects-and-artifacts/replit-deployments)，[Lovable 支持发布网站](https://docs.lovable.dev/features/publish)，也提供[代码同步与导出途径](https://docs.lovable.dev/integrations/github)。星桥应通过具体业务场景的完成质量、修改后的可控性和清楚的费用建立选择理由。

竞争不只来自其他 AI 产品，也来自客户正在用的表格、聊天群、现成业务软件和人工处理。若表格已经足够好，星桥不能仅靠“用了 AI”说服客户迁移。

### 首批客户与使用者

| 角色 | 首期选择 | 要解决的问题 |
| --- | --- | --- |
| 应用创建者 | 小团队业务或运营负责人，熟悉表格与在线工具，但没有专职开发资源 | 把反复登记、分配和跟进的工作整理成可用工具 |
| 应用使用者 | 负责人邀请的同事 | 快速处理业务，不需要学习编程或与 AI 对话 |
| 购买者 | 团队负责人或企业经营者 | 确认节省的时间、持续费用和数据是否可控 |
| 试用协助者 | 熟悉技术的内部用户 | 发现产品缺陷；其评价不能代替业务客户的需求验证 |

首期不承接强监管数据、关键交易系统、大型企业定制，以及承诺全天候服务的核心业务。普通聊天仍保留，但“通用聊天、写作、音乐、工作流、应用开发全能平台”不作为近期定位。

## 2 当前能力与目标体验的区别

以下“已有”以仓库验收记录为依据，不代表本轮重新完成线上验收。

| 范围 | 已有基础 | 本轮确定的改造方向 |
| --- | --- | --- |
| 编程与文件 | 聊天编程、个人持久文件、预览编辑与任务反馈已有实现 | 按项目组织目标、对话和成果，让用户知道正在修改什么 |
| 构建与发布 | 构建、推送、发布和故障处理已有实现 | 从“部署成功”升级到“业务验收通过且可交付” |
| 工程恢复 | 源码恢复点、差异和恢复到新目录已有验收 | 关联发布版本，分别解释源码、线上应用和业务数据的恢复范围 |
| 额度与套餐 | 可配置权益和模拟订单已有基础 | 套餐先说明业务价值，再展示实际额度、费用与边界 |
| 数据保护 | 已完成合成数据的本地恢复演练 | 真实客户数据试点前补齐备份、恢复和访问验证；本地演练不等于整机故障保护 |
| 商业验证 | 尚未形成可证明的客户留存与真实付费结论 | 通过同场景小规模试点测量独立完成、持续使用和实际付款 |

## 3 首个场景是内部售后工单

### 最小业务范围

待验证的场景假设是：负责人通过表格和聊天消息记录客户问题，容易遗漏处理人、进度和后续跟进。首个模板让同事在同一处登记、分配、更新和查询工单。

首版提供工单编号、创建时间、客户代称、问题描述、负责人和状态。状态先采用“待处理、处理中、已解决”，支持列表筛选与授权导出。用户可以通过对话调整字段、展示和简单规则，但不能把模板变成无限定制承诺。

先使用示例数据。导入已有业务数据时，必须先预览字段映射与导入结果；复杂表格公式、多表关联和历史数据清洗不进入首版范围。

首版不包含完整 CRM、客户自助门户、复杂审批、即时通信、财务结算或多企业组织管理。先验证内部协同，再决定是否开放给客户访问。

### 用户能看懂的验收清单

1. 新建一条工单，重新进入页面后仍能找到。
2. 分配给一位受邀同事，对方能看到并更新处理状态。
3. 按负责人和状态筛选，结果与示例记录一致。
4. 有导出权限的人可以导出预期记录；未获授权的人不能访问或导出。
5. 修改应用草稿时，已发布应用继续可用；发布后，同事访问的是经过确认的新版本。

“有一个能打开的网页”不能替代上述业务验收。权限、保存、计算或数据范围不正确时，产品不得显示“业务已完成”。

## 4 项目是持续工作的入口

聊天是提出需求和修改意图的主要方式，项目承接长期上下文和成果。用户隔几天回来，应能直接找到正在使用的应用、待完成的修改和下一步，而不必从旧聊天里推断状态。

| 用户概念 | 含义 | 默认展示 |
| --- | --- | --- |
| 我的空间 | 用户长期拥有的项目和文件 | 最近项目、使用量、进入文件的入口 |
| 项目 | 一个持续维护的业务目标 | 简短目标、当前草稿、相关对话、已发布应用 |
| 文件 | 上传资料、工程源码和生成结果 | 文件树、预览与编辑、上传下载和必要的管理操作 |
| 已发布应用 | 同事可以访问的业务工具 | 地址、访问范围、运行状态、版本和费用 |

一个项目可以有多个对话；普通聊天不必创建项目。首期一个项目重点维护一个主要应用，不同时引入复杂多服务编排的用户概念。

个人文件不因聊天删除、任务失败、暂停应用或套餐到期而直接删除。项目与文件的关联不能代替明确的数据删除确认。

### 项目工作台布局

```text
项目名称 · 一句话目标                  草稿有修改    预览    发布
──────────────────────────────────────────────────────────
简洁导航      对话与修改要求                  应用预览
最近项目      AI 的阶段结果和待确认事项       示例数据 / 当前草稿
我的文件      连续的聊天输入区                业务验收清单
已发布应用
──────────────────────────────────────────────────────────
用量与套餐位于个人菜单；文件和代码按需展开，不挤占主工作区。
```

这是信息布局约定，具体比例和移动端表现需经过原型验证。普通聊天主界面保持稳定；进入项目后明确显示项目名称和修改对象。预览可展开、收起或并排查看，窄屏按需切换，不同时铺满聊天、文件树、日志和应用卡片。

模型和编程高级设置保留可达入口，但完成业务不应要求用户理解 OpenHands、MCP 或底层组件名称。

## 5 从需求到持续使用的流程

```mermaid
flowchart LR
    A[选择业务模板或描述需求] --> B[确认目标与验收清单]
    B --> C[生成草稿与示例预览]
    C --> D[通过对话修改]
    D --> E[完成业务验收]
    E --> F[确认访问范围与费用并发布]
    F --> G[同事使用应用]
    G --> H[带着新需求返回项目]
    H --> D
```

### 需求确认

先问必要的三到五个问题：谁使用、处理什么工作、需要哪些信息、怎样算完成、谁能看到。给出简短目标和验收清单，由用户修正后开始。已有模板可带入默认答案，避免长篇问卷。

### 创建与修改

默认基于已验证模板生成示例。聊天展示“正在准备页面”“正在检查保存功能”等实际进度；工具细节收起，但结果、等待确认、失败原因必须直接可见。没有实际进展时不能用重复动画或重复文字制造正在工作的假象。

修改前确认当前项目和目标，避免把另一个对话的内容误当需求。发生范围明显扩张时，解释新增工作和费用，不能擅自无限执行。

### 预览与验收

用户直接操作预览中的业务功能，聊天负责解释和修正。示例数据应有明确标记。预览、草稿与已发布版本必须可区分；AI 自称“测试通过”不能替代对应结果和必要的用户确认。

### 发布与分享

发布确认页只呈现关键问题：发布哪次修改、谁能访问、是否影响已有数据、预计持续费用以及额度是否足够。发布结果显示地址、当前状态和验收结果。链接可访问但业务检查失败时，显示具体未通过项。

首期以邀请同事访问为主要路径。应用使用者不需要购买 AI 创建套餐，也不默认拥有项目源码、模型额度和发布权限。多人共同编辑工程属于后续独立能力，不与应用访问权限混淆。

### 返回与迭代

返回项目时显示“线上正在使用的版本”和“尚未发布的修改”。用户可以提出新需求、查看预览，再决定是否发布。常用操作如访问应用、暂停、查看版本和导出仍提供直接按钮，不强制把每次点击改成聊天指令。

## 6 关键页面与必需状态

| 页面 | 用户首先看到的内容 | 必须明确的状态 |
| --- | --- | --- |
| 产品介绍与开始页 | 一个真实业务演示、适用人群、交付结果、体验边界 | 演示不冒充客户案例，不承诺所有需求都能一次完成 |
| 我的空间 | 最近项目、项目目标、继续工作入口、用量摘要 | 空空间有模板入口；加载失败不伪装成没有文件 |
| 新建项目 | 售后工单模板、需求说明、少量确认项 | 免费体验范围、预计消耗、暂不支持的需求 |
| 项目工作台 | 对话、当前草稿预览、验收清单 | 执行中、待用户确认、已停止、失败、结果待核验 |
| 应用详情 | 可访问地址、版本、访问成员和状态 | 线上应用状态与最近一次发布结果分开展示 |
| 个人用量与套餐 | 当前实际生效权益、剩余额度和持续费用 | 模型额度与资源有效期不同；订单到账和资源开通进度分开 |
| 管理员工作台 | 需要处理的用户问题、失败任务、费用异常 | 处理依据、影响范围、操作记录和后续跟踪 |

界面以中文和业务词语为主，数字单位统一，表单标签对齐，重要信息不过度留白。亮暗主题、窄屏、键盘操作和加载过程均属于验收范围。用户找不到发布、容量或编辑入口，不能以“功能已存在”判定通过。

## 7 失败与恢复的产品规则

每次失败先回答四件事：完成了什么、什么没有完成、已有数据和线上应用是否受影响、下一步是什么。原始日志作为补充入口。

自动修复必须受次数、时间和费用上限约束，实际默认值在试点前确定并公示。重试预算耗尽后停止，保留成果并给出可执行的选择。发布结果不明确时先核验，不能让用户因点击重试重复发布或重复付费。

| 情况 | 用户应看到的结果 |
| --- | --- |
| 查询暂时超时 | 上次确认的状态、最后确认时间、正在重试；不直接宣称应用失败 |
| 新版本构建失败 | 本次修改未发布，指出原因；如旧应用仍运行，应明确告知 |
| 发布结果不明确 | 正在核验结果，防止重复操作；超出自动核验范围才进入人工处理 |
| 模型额度不足 | 本次任务停止在何处、保留了什么、补充额度后能否继续 |
| 暂停应用 | 停止哪些运行费用、仍保留哪些数据及费用；不能笼统写“不再收费” |
| 恢复历史版本 | 明确恢复源码还是线上应用；涉及数据库结构或业务记录时单独说明并确认 |

源码恢复点不是完整业务备份。切换旧应用版本不应悄悄删除新产生的工单。无法兼容已有业务数据时，必须阻止误导性的一键回滚，提供明确的处理方案。

## 8 套餐与收费表达

目标收费结构为“持续使用应用的服务套餐，加上清楚可控的 AI 使用额度”。是否按月、具体价格、包含额度和超额规则，须经试点成本与付费意愿验证。本次不修改已有订单、金额、有效期和实际权益。

| 层级方向 | 用户购买的价值 | 需要清楚展示的权益 |
| --- | --- | --- |
| 体验套餐 | 判断能否做出适合自己的一个小工具 | 可体验的创建与发布范围、模型额度、空间、运行限制和保留规则 |
| 基础套餐 | 持续使用和迭代少量业务应用 | 应用数量、可选运行规格、空间与数据库上限、模型额度、代码运行限制 |
| 更高个人套餐 | 更多应用、数据和修改需求 | 提高后的实际上限和持续费用，不能只写“更强能力” |
| 团队套餐，后续验证 | 多位创建者协作与管理 | 创建者席位、共同编辑、角色和支持承诺；未实现前不作为已售权益 |

注册赠送 1 美元是现有体验安排。它应帮助用户完成有限场景的价值验证，不意味着任何需求都能在 1 美元内完成。若目标场景实际成本超过赠送额度，应先调整模板和体验范围，再评估补贴，避免流程做到一半突然强制付费。

套餐售价与模型额度分别配置。例如售价 10 元、其中模型额度按 5 元配置、结算规则为“1 美元 = 7 元人民币”，模型额度就是约 0.7143 美元，而不是 10 美元或 5 美元。这个数值仅解释规则，不是本轮价格决定；界面必须展示实际订单规则与到账额度。

Tokens 可用于查看实际消耗和估算，但不同模型、输入输出价格不同，不应把美元余额包装成固定可用 Token 总数。空间应显示实际生效总量及文件、数据库等组成，子上限的包含关系要清楚，不能让用户把多个上限误认为额外赠送。

升级前显示增加的权益、何时生效、此次收费和后续费用。AI 额度用尽与应用服务到期分别处理。欠费不触发无提示的数据销毁；保留期、导出窗口和删除规则必须在真实收费前确定。

平台故障、模型生成错误、需求变更三类成本分别记录。补偿规则要有明确适用条件和审批记录，不能承诺所有失败均免费，也不能让用户为无限自动重试买单。真实支付上线前，模拟订单与真实收入必须严格区分。

## 9 信任与管理员职责

用户应能理解谁能访问自己的应用、文件和数据，查看重要变更，导出可继续使用的成果。导出目标包括源码、业务数据、附件和启动说明；缺失部分需在导出前说明，不把“下载源码压缩包”等同于完整迁移。

管理员平台继续独立，重点支持用户问题处理、套餐权益、预算与用量解释、服务异常、待核验任务和操作审计。管理员不能把“用户数据可能受影响”隐藏在内部状态里，也不能通过修改订单历史来掩盖补偿。

当前无已验证的主机外备份。补齐恢复和访问验证前，试点只能使用示例或可重建数据；不能宣传生产数据保护或全天候可用承诺。保留周期和服务承诺以完成实际验证为前提。

## 10 已有用户的过渡方案

改造优先调整组织方式和引导，不自动迁移或重命名用户文件，也不根据文件夹名称猜测项目归属。

1. 已有用户可以从现有文件夹“关联为项目”；先展示目录、已有应用及对话候选，由用户确认。
2. 无法确定归属的文件继续在“我的文件”中可用；关联失败不能导致原文件入口消失。
3. 已有聊天保留历史与访问方式；普通聊天不强行转为项目，项目对话不自动获得跨项目文件权限。
4. 已发布应用保留访问地址和现有状态，关联项目不触发重新发布。
5. 已购买权益继续按实际生效规则展示；改套餐文案不能静默改额度或让用户重新购买。
6. 先对小范围试用用户开放新工作台，保留返回原入口的路径。完成旧文件、旧对话、旧应用和权益回归后再扩大范围。

## 11 功能取舍与扩展条件

| 决策 | 范围 | 原因 |
| --- | --- | --- |
| 优先完善 | 项目入口、业务模板、可操作预览、验收清单、可靠发布、修改与恢复、清楚费用 | 直接决定能否完成一次有用交付并持续使用 |
| 保留但降低干扰 | 文件编辑、模型选择、编程高级设置、代码运行、已有 MCP 能力 | 服务已有用户和复杂需求，不占据新用户首屏 |
| 暂缓新增 | 音乐制作、公共模板市场、多工作流引擎、完整团队工程协作、大而全的集成中心 | 在验证核心场景前增加选择负担和维护成本 |
| 有证据再推进 | 自动提醒、周期汇总、外部系统连接 | 现有应用用户反复提出并愿意为之使用或付费时，做单一场景试点 |

Langflow 可以成为后续自动化能力的实现选项，但用户购买的是“每天自动汇总未处理工单”等结果。近期不安装它来充当功能丰富度，不把它变成普通用户必须学习的第二套编辑器。技术选型留到业务试点成立后比较。

## 12 成功标准与待验证问题

核心指标是**每周真正被团队用于处理业务的应用所覆盖的团队数**。不能用注册人数、生成代码量或部署次数替代。

“真正使用”至少要有非平台测试产生的有效业务记录，以及受邀同事的处理动作。排除内部自动化验收、样例点击和只有创建者自己浏览的演示；详细口径见[路线图的验证指标](product-optimization-roadmap.md#6-指标与证据口径)。

下一轮要回答：售后工单是否足够痛、模板能否覆盖共性需求、负责人能否独立交付、同事是否愿意继续用、真实成本是否允许合理售价、客户是否愿意为持续服务付款。答案不足时收窄或调整场景，不以继续增加组件代替判断。

旧方案中的所有人群、先购买才能开始的默认引导以及多能力标签扩张，不再作为当前产品方向。历史实现与验收记录继续保留；本设计不宣称已完成对应改造。
